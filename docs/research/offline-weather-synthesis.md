# 离线天气推算（Offline Weather Synthesis）

> **这份文档解决什么问题**
> NowWeather 依赖 API（Open-Meteo / UApiPro）获取城市实况。但网络会断，而且即使在线，
> 实况也有 15 分钟（Open-Meteo）到十几分钟（UApiPro）的更新间隔。
> 所以需要两件事：
>
> - **A. 插值/推算**：两次真实数据之间平滑推演（也叫 *temporal downscaling* / *nowcasting by blending*）；
> - **B. 完全离线**：从来没拿到过数据时，仅凭「地点元数据」推算接近真实的天气
>   （气象学上就是 *climatological synthesis*，即用气候态合成一个合理的瞬时天气）。
>
> **本文档的定位**：给出可直接照着写 Java 的公式、每组系数的来源与置信度、
> **以及诚实的精度上限**。凡是没有文献依据的地方，本文档明确标注为「工程近似」。
>
> ⚠️ **先说结论，避免后续被误读**：离线推算**不能**预测天气。
> 它在离线第 1 天能超过「气候平均」这个基线，到第 3 天就和基线打平，
> 第 7 天以后**明显不如**直接查当月气候平均。它的真正价值是
> 「让没有数据时的天气看起来合理、连贯、不跳变」，而不是「猜对明天会不会下雨」。

```

dayAngle     = 2π * (dayOfYear - 1) / 365.25      // 弧度，Spencer 用的日角
```

## 2. 温度模型（最重要）

温度是**唯一**能在离线状态下做到「相当接近真实」的量。降雨/云的命中率主要来自基础概率，
不是模型本事（见 §3.3 与 §8）。所以工程投入应集中在温度上。

### 2.1 季节性基准温度

#### 公式（可直接实现）

```
T_season(dayOfYear, lat) =
        T_annual_mean(lat, elevM)
      + A(lat, continentality)
      * cos( 2π * (dayOfYear - peakDay(lat)) / 365.25 )
```

其中

```
peakDay(lat) = 202 + (hemisphere == SOUTH ? 182.6 : 0)      // 见 2.1.3
T_annual_mean = T_ref(absLat) - lapseRate * (elevM / 1000)   // 见 2.2
```


> **重要警告**：R² 只有 **0.60**。纬度**单独**解释不了振幅——Miami（25.8°N）振幅 3.5 K，
> 而同纬度的 Riyadh 是 11.3 K，相差 3 倍多。差别来自**海洋性 vs 大陆性**（见 §2.4）。
> **不要把这条回归当作主模型**，它只适合在完全没有海陆信息时兜底。
>
> ✅ **更好的方案已经实测拟好，见 §2.4 方案 D**：
> `A = sin(|lat|)·(9.1 + 18.1·d/(d+400))`，只需 `|lat|` 与**距海岸距离 `d`**，
> 留一交叉验证 RMSE **2.5 K**（vs 只用纬度的 4.45 K，**误差降低约 40%**），
> 且只需要一张 **约 2 kB** 的陆海位图。**下面的查表法只在连掩膜都没有时使用。**

更可靠的**查表法**（按 |纬度| 分档，取本实测中位数并参考海洋/大陆差异）**【工程近似】**：

| absLat 区间 | A（海洋性/沿海） | A（内陆/大陆性） |
| --- | --- | --- |
| 0–10° | 1 | 3 |
| 10–20° | 2 | 6 |
| 20–30° | 4 | 10 |

> 说明：Yakutsk（62°N，极端大陆性）实测 28.7 K 是最极端个案；表中 60–75° 大陆性给 22 K 是

**文献对照（高置信度）**：一阶谐波（年周期正弦）描述季节温度循环是气候学标准做法，
其残差在小纬度 <1 K、中纬度 2–4 K、极端大陆性 >5 K，与上表一致。
`peakDay` 相对夏至滞后约 3–4 周也是标准结果（见 2.1.3）。

#### 2.1.2 南半球相位翻转 —— **已实测验证**

把北半球测站的峰值日加上 **182.6 天**（= 365.25/2），与南半球实测对比：

```
北半球（|lat|>15°）实测峰值日： 206, 200, 210, 204, 208, 199, 194, 197
                                 → 平均 202.2（范围 194–210）

预测南半球峰值日 = 202.2 + 182.6 = 384.8 → mod 365.25 = 19.6（1 月 19–20 日）
南半球实测：Sydney 18（1/18）、SaoPaulo 13（1/13）、Windhoek 360（12/26）
              → 平均 15.5（不含 Windhoek 异常值），或 8.7（含）
```

**结论：`phase shift = +182.6 天` 的经验法则成立，误差约 ±4～11 天**，
而这一点误差本身就在峰值日的站间离散度（194–210，即 ±8 天）以内。
所以实现时**直接用 `peakDay = 202 + (SOUTH ? 182.6 : 0)` 就够了**。
（置信度：**高**——本项目实测 14 站验证。）

#### 2.1.3 相位滞后（peakDay 的物理含义）

太阳辐射的峰值在**夏至**（北半球 doy 171.5 ≈ 6 月 21 日）。气温峰值因为
地表/海洋热惯性而滞后。实测滞后量：

| 测站 | 峰值日 | 距夏至滞后 |
| --- | --- | --- |
| Cairo | 206 | 34.5 d |
| Miami | 210 | 38.5 d |
| London | 208 | 36.5 d |
| Hangzhou | 204 | 32.5 d |
| Riyadh | 200 | 28.5 d |
| Moscow | 199 | 27.5 d |
| Anchorage | 197 | 25.5 d |
| Yakutsk | 194 | 22.5 d |
| Sydney | 18 | 28.2 d（相对 12/21） |
| SaoPaulo | 13 | 23.2 d（相对 12/21） |

**平均滞后 ≈ 31 天（北半球），≈ 26 天（南半球）**，即「最热的一天在夏至后约一个月」。
这与气象学上常引的「3–4 周滞后」一致。置信度：**高**（本项目实测）。

> 工程含义：**不要**把 `peakDay` 设成夏至（171.5）。设成 202 才符合实际。
> 注意 Yakutsk 这类极端大陆性测站滞后更短（22.5 d）——因为陆地热容小，响应更快。
> 这正是 §2.4 里「大陆性 → 振幅大 + 滞后短」的物理原因。

### 2.2 海拔递减率

#### 文献值（置信度：高）

| 递减率 | 数值 | 来源 |
| --- | --- | --- |
| **标准/环境大气递减率** Γ | **6.5 K/km** | 国际标准大气 ISA / US Std Atm 1976 / ICAO。`T = 288.15 K − 6.5 K/km · H`（H ≤ 11 km）。[Stull, *Practical Meteorology* Ch.1](https://www.eoas.ubc.ca/books/Practical_Meteorology/) |
| **干绝热递减率** Γd | **9.8 K/km** | 同上，Stull eq. 3.8 |
| **湿（饱和）绝热递减率** Γm | **约 4–9 K/km，典型 5–6 K/km** ⚠️ | 见下方说明 —— 这是**教科书范围，本次调研未能核实一手来源** |

> ⚠️ **湿绝热递减率这一行是本文档唯一没有一手来源的"文献值"**。
> 本次调研尝试核实「4–9 K/km，典型 5–6」时，AMS Glossary 对全部请求返回 403，
> ScienceDirect 不可达，Stull 原文只说 Γs「**会变化，但永远是正数**」且 Γs ≤ Γd，
> **没有给出数值范围**。
> 唯一可核实的数值来自 Stull Ch.5 的湿绝热表：沿 θ_w = 20 °C 的湿绝热线，
> 温度从 100 kPa 的 20 °C 降到 50 kPa 的 −8.8 °C，即约 5.5 km 内平均 **≈5.1 K/km**
> —— 与「暖湿近地面约 5–6 K/km」一致（**派生值**）。
> **结论：不影响我们的实现**（见下），但引用时请标注为教科书常识而非已核实文献。

#### ❗「要不要考虑湿绝热/干绝热的区别？」—— 答案：**不要**

对**天气模组**这个用途，用 **6.5 K/km** 是对的，理由有三条：

1. **绝热递减率（9.8 / 4–9）描述的是「气块抬升时的冷却」，不是「两地之间的温差」。**
   我们要做的是「把 A 地（海拔 z₁）的气温换算到 B 地（海拔 z₂）」，
   这属于**环境递减率**（environmental lapse rate），标准值就是 6.5 K/km。
   干/湿绝热的区别只在你追踪一个气块垂直运动时才需要。
2. **实测证实 6.5 更接近真实**：Alps 实测年均递减率 **5.4–5.8 K/km**（Rolland 2003, *J. Climate* 16:1032），
   夏季更陡。智利干旱安第斯 [Front. Earth Sci. 2022](https://doi.org/10.3389/feart.2022.875795)
   用 **5.5–6.5 K/km** 能很好地复现观测雪线。
3. **同一份再分析数据的自带处理就是这么做的**：[meteostat 的插值 API 文档](https://dev.meteostat.net/python)
   把默认值写死为 `lapse_rate=6.5 °C/1000 m`、`lapse_rate_threshold=50 m`；
   FAO-56 气压公式 `P = 101.3·((293 − 0.0065·z)/293)^5.26`
   （[FAO-56 Ch.3](https://www.fao.org/4/x0490e/x0490e07.htm)）里也直接嵌了 **0.0065 K/m**。
   两个独立工程实现都选了 6.5。

#### ⚠️ 但 6.5 有一个已知缺陷（重要，文献支撑）

[Lundquist & Cayan (2008), *J. Appl. Meteor. Climatol.*, doi:10.1175/2007JAMC1565.1](https://doi.org/10.1175/2007JAMC1565.1)
的原话是：6.5 K/km「**只适用于日最高温**，对日最低温和日均温常常严重高估」，
并建议使用**逐月**递减率。Córdova et al. (2016) 在厄瓜多尔安第斯实测：

| 量 | 递减率 |
| --- | --- |
| 日均温 Tmean | 6.9 K/km |
| **日最低温 Tmin** | **5.5 K/km** |
| 日最高温 Tmax | 8.8 K/km |

**工程建议**【工程近似】：

```
lapseForTmax = 8.8 K/km          // 白天对流混合强，更接近干绝热
lapseForTmin = 5.5 K/km          // 夜间逆温/边界层稳定，递减率小
lapseForTmean = 6.5 K/km         // 标准值
```

如果实现成本只允许一个数，用 **6.5 K/km**（置信度**高**）；
如果要更准，按上表分 Tmax/Tmin（置信度**中**，依据单一区域研究 + Lundquist & Cayan 的结论）。

**为什么 6.5 是对的而 9.8 是错的（物理原因，置信度：高）**：
Stull Ch.3 说明真实大气经历「**湿对流调整**（moist convective adjustment）」，
把初始较不稳定的递减率调整到**更稳定**的状态，
「其结果有时是一个**接近标准大气**的垂直梯度」。也就是说：
**9.8 K/km 只在「干绝热充分混合的气柱」中成立，而自由大气不是**。
具体量级：把一个 1500 m 测站按 9.8 K/km 折算到海平面会加 **14.7 K**，
而按 6.5 K/km 只加 **9.8 K** —— **多出的 4.9 K 是纯粹的假订正**。

> 这解释了 Lundquist & Cayan 为什么说 6.5 对 Tmax 合适：白天对流混合强，
> 边界层接近干绝热混合 → 递减率接近 9.8；而 8.8 K/km（Córdova 实测）正落在这两者之间。
> 夜间边界层稳定甚至逆温 → Tmin 递减率被压到 5.5 K/km。

> ⚠️ **另一个坑**：如果游戏坐标的海拔与 API 网格海拔差别很大（例如 API 报的是 13 m，
> 玩家在 1500 m 高原），**必须先做海拔订正再落地**。
> 这正是 `docs/BIOME_CLIMATE.md` 里温度校验的物理依据。
> 另外，递减率只在**自由大气**成立；高原上的实际递减率会因地表加热而偏小，
> 所以对 >3000 m 的高原不要过度依赖这条。

**Lundquist & Cayan (2008) 的完整建议（原文结论，置信度：高）**：
基于美国爱达荷州南部 10,000 km² 区域、14 个站、1989–2004 的逐日 Tmax/Tmin/Tavg：

1. 「常用的环境递减率（通常取 **−0.65 °C/100 m**）**只适用于最高温**，
   且**常常严重高估 Tmin 与 Tavg 的递减率**」；
2. 「**区域递减率的表现在 Tmin 和 Tavg 上优于环境递减率**，
   但对某些月份，**逐月递减率**能预测得更准……
   **逐月递减率被推荐为「效果与实现简便性的实用折中」**」；
3. 季节结构：Tmax 递减率有**明显的季节趋势——夏季更陡、冬季更平**；
   而 Tmin/Tavg 递减率更多变，**春季最陡、盛夏最平**；
4. 天气尺度：**暖气团对应更陡的 Tmax 递减率**，
   **干气团对应更平的 Tmin 递减率**；「**最大的日较差由干燥热带条件
   （晴空、高太阳输入）产生**」。
5. **雪/相态用途**：用 **5.5–6.5 K/km**，并记住雪线平均落在
   外推 0 °C 等温线**下方约 280 m**（智利干旱安第斯实测，见 §3.1）。
6. **精度预期**：Rolland (2003) 对 640 个阿尔卑斯站交叉验证给出的插值精度是
   「**多数情形约 1 °C**」，且**最高温、夏季**最好；**Tmin 在冬季更差**。

> **对我们的工程含义**：上面的「逐月递减率」建议，我们**做不到**（离线时没有本地测站对）。
> 所以实现里用单一 6.5 是**合理的降级选择**，
> 但要认识到：**海拔订正这一环本身就有约 1 °C 的固有误差**，
> 且对 Tmin 会系统性地订正过头。这部分误差已经包含在 §10.1 的 ±3 K 预算内。

### 2.3 昼夜曲线

#### 2.3.1 形状与关键时点

**Tmin 出现在日出前后，Tmax 出现在午后。** 具体时点（文献值，置信度**高**）：

| 事件 | 时点 | 依据 |
| --- | --- | --- |
| **Tmin** | **日出时刻**（或日出后 0–30 分钟） | 夜间辐射冷却在日出瞬间转为加热，最低温出现在日出前后 |
| **Tmax** | **地方太阳时 14:00–15:00**，即**正午太阳时后约 2–3 小时** | 地面能量收支由正转负的时刻滞后于正午辐射峰值 |

本项目实测的日较差（DTR）见 §2.3.3 表，与上述一致。

#### 2.3.2 可实现的曲线

气象学上常用两种形态，本文档给出**分段余弦**方案（推荐，因为它把
「Tmin 在日出、Tmax 在午后」这两个硬约束直接编码进去了）：

```
输入：sunriseHour, sunsetHour   // 地方太阳时，小时（小数）
      Tmin, Tmax                 // 当日最低/最高温

// 关键时点
tMinHour = sunriseHour                       // Tmin 在日出
tMaxHour = solarNoonHour + 2.5               // Tmax 在正午后 2.5 小时（≈14:30）
         ≈ (sunriseHour + sunsetHour)/2 + 2.5

if  tMinHour <= t < tMaxHour:                // 升温段（上午到午后）
    phase = (t - tMinHour) / (tMaxHour - tMinHour)          // 0..1
    T = Tmin + (Tmax - Tmin) * 0.5 * (1 - cos(π * phase))   // 半余弦，平滑起止
else:                                        // 降温段（午后到次日日出）
    // 注意跨午夜：把时间轴线性化
    span  = (24 - tMaxHour) + tMinHour
    phase = ((t - tMaxHour + 24) mod 24) / span              // 0..1
    T = Tmin + (Tmax - Tmin) * 0.5 * (1 + cos(π * phase))   // 半余弦，反向
```

- **升段用半余弦、降段用半余弦**，保证在 Tmin/Tmax 处导数为 0（曲线光滑，不会出现尖角）。
- 与纯正弦 `T = Tmean + (DTR/2)·cos(...)` 相比，这个方案的关键优势是
  **Tmin 和 Tmax 的时点可以分别指定**，而纯正弦强迫两者以 12 小时等距分布——那是不符合实际的
  （白天升温段通常 8–10 小时，夜间降温段 14–16 小时）。
- 文献支撑：Parton & Logan (1981) 的空气温度日变化模型即采用「分段正弦/余弦」结构
  （*Agric. Meteorol.*，[记录](https://www.sciencedirect.com/science/article/abs/pii/0002157181901059)，置信度**中**——原文付费，本文档只确认其结构为分段正弦）。
  上述具体写法是 **【工程近似】**，但形态与文献一致。

**更简单的备选（纯正弦 + 相位）**【工程近似】：

```
T(t) = T_season_daily_mean + (DTR/2) * cos( 2π * (t - tMaxHour) / 24 )
```

代价是 Tmin 会被强制出现在 Tmax 后 12 小时，通常在半夜，**这与「Tmin 在日出」矛盾**，
日出晚的冬季误差可到 3–5 °C。**不推荐**，只在需要极简实现时用。

#### 2.3.3 云量与湿度如何削减日较差 —— **已实测**

用 ERA5 逐日数据，定义：
`日照充足日` = `sunshine_duration > 0.75 × 43200 s` 且 `precip < 0.2 mm`；
`阴天` = `sunshine_duration < 0.20 × 43200 s`。结果：

**结论（本项目实测，置信度：高）**：

1. **平均日较差与平均相对湿度强线性相关**：

   ```
   DTR ≈ 18.10 − 0.1398 * RH_mean_percent      [K]        R² = 0.797   n = 14
   ```

   代入：`RH=85% → 6.2 K`；`RH=50% → 11.1 K`；`RH=25% → 14.6 K`。
   **这是本文档中拟合得最好的一条经验关系（R²=0.80）**，强烈推荐使用。
   标注为**【工程近似】**（公式形式是本文档构造的），但其物理含义明确
   ——湿度高 → 水汽多 → 夜间向下长波辐射强、白天蒸发耗热 → 日较差小。

2. **云量削减日较差的幅度约 4–7 K（中位数约 5.5 K）**，
   在干旱地区可达 8–10 K，在常年高湿的热带只有 2–5 K。

**文献对照（置信度：高）**：Dai, Trenberth & Karl (1999), *J. Climate* **12**:2451–2473,
[doi:10.1175/1520-0442(1999)012<2451:EOCSMP>2.0.CO;2](https://doi.org/10.1175/1520-0442(1999)012%3C2451:EOCSMP%3E2.0.CO;2) 原文：

> 「**云，加上土壤湿度和降水的次生阻尼作用，在多数陆地区域可把日较差相对晴天削减 25%–50%。**」
> 「低云云的削减效率最高……中云和高云只有温和的阻尼作用。」
> 「**高达 80% 的日较差方差可由云与降水记录解释。**」
> 并特别指出：水汽「同时抬高夜间与白天温度，对日较差影响很小」。

→ 这两个数字（**相对削减 25–50%**、**方差解释率 80%**）比我上面的绝对值更有引用价值。
把它换算成折减系数即 **`cloudFactor ∈ [0.50, 0.75]`**（阴天），低云可低至 **0.50**。

> ⚠️ **本项目实测值偏大，需注意数据源差异**：我用 ERA5 测得的「晴天 vs 阴天」落差是
> 4–10 K（相对削减常在 40–60%），**高于** Dai 1999 的 25–50%。
> 原因很可能是 **ERA5 是约 30 km 的网格平均，本身就会平滑掉局地极值**，
> 使「晴天」不够晴、「阴天」不够阴，从而**夸大**了对比落差。
>
> **交叉验证**：NOAA 1991–2020 站点气候常态（NCEI normals API）给出
> Miami 年均日较差 **7.5 K**、Honolulu **7.3 K**；而我的 ERA5 拟合是 Miami **5.4 K**。
> 相差约 2 K（相对 39%），方向一致地显示 **ERA5 低估日较差**。
> 本报告里 §2.3.3 的相对大小与排序可信，但**绝对数值应视为下限**。
> 若你的 `DTR_clear` 拟合用的是 ERA5，实际落地时可整体上调约 1–2 K。
> （置信度：**中** —— 这是两个数据源的对比推断，不是严格验证。）

**落地方案**【工程近似】：

```
// 从生物群系湿度（0~1）与天气状态得到目标日较差
DTR_clear(bio, lat) = clamp(18.10 - 0.1398 * (bio.humidity * 100), 4, 16)
// 注：ERA5 拟合值偏小，实践上可取 DTR_clear + 1.5（见上方数据源差异说明）

// 云量折减系数：与 Dai 1999 的「相对削减 25–50%」对齐
cloudFactor = switch (weatherType) {
    CLEAR        -> 1.00
    PARTLY_CLOUDY-> 0.85
    CLOUDY       -> 0.72
    OVERCAST     -> 0.55
    RAIN/SNOW    -> 0.50
    THUNDERSTORM -> 0.50    // 低云削减效率最高，但不低于 0.50
}

DTR = DTR_clear * cloudFactor
Tmax = T_season + DTR/2
Tmin = T_season - DTR/2
```

> 注意 `DTR_clear` 的上下限（4~16 K）是工程裁剪，用来防止湿度字段异常时算出离谱值。
> `cloudFactor` 的下限 **0.50** 有文献依据（Dai 1999 的 50% 上限），不要再往下压。

### 2.4 内陆度 / 海洋性

振幅（§2.1.1）与相位滞后（§2.1.3）都强烈依赖海陆位置，而**这两者都有实测证据**：
海洋性 → 振幅小、滞后长（Miami 25.8°N：A=3.5 K、滞后 38.5 d）；
大陆性 → 振幅大、滞后短（Yakutsk 62°N：A=28.7 K、滞后 22.5 d）。

#### 方案 A（有海陆数据时，推荐）

按「到最近海岸线的距离 D_coast」插值，`w = clamp(D_coast / 500km, 0, 1)`：

```
A              = lerp(A_maritime(absLat), A_continental(absLat), w)
peakDay        = lerp(peakDay_maritime, peakDay_continental, w)
                 // 北半球：海洋 208, 大陆 197（本项目实测两端值）
```

系数表见 §2.1.1 的查表法。置信度：**中**（两端有实测支撑，中间插值形式是【工程近似】）。

#### 方案 B（没有海陆数据时的降级方案）

**Minecraft 的坐标是虚拟的，与真实地理无关**，所以**不能**用游戏内坐标判断海陆。
降级路径按优先级：

1. **生物群系湿度字段**（`bio.humidity`，0~1）——这是最好的可用代理：
   ```
   continentality = 1 - bio.humidity          // 0 = 极海洋性，1 = 极大陆性
   A       = lerp(A_maritime(absLat), A_continental(absLat), continentality)
   ```
   依据：湿润气候通常受海洋调节（高湿 → 低 DTR，§2.3.3 已实测 R²=0.80），
   而干旱内陆气候日较差大。**注意这是相关而非因果**——沙漠可以临海（如利马）。
   置信度：**低**【工程近似】。

2. **生物群系气候大类**（`climateClass`）——若没有湿度字段，用大类查表：

   | climateClass | continentality 建议值 |
   | --- | --- |
   | `OCEANIC` / `TEMPERATE`（沿海标签） | 0.2 |
   | `TEMPERATE` | 0.5 |
   | `ARID` / `DESERT` | 0.8 |
   | `CONTINENTAL` | 0.9 |
   | `POLAR` | 0.6 |
   | `TROPICAL` | 0.3 |

   **注意：`ClimateClass` 现有枚举里如果没有这些值，就用 `bio.humidity` 反推，或直接用常量 0.5。**

3. **最终兜底**：`continentality = 0.5`（取中），振幅用 `A(lat) ≈ −1.01 + 0.289·absLat`，
   并接受 ±1 档的误差（由 §2.1.1 的 R²=0.60 可知，这等效于振幅误差可达 ±5 K）。

#### 方案 C：用「大陆度指数」代替主观的 0~1 插值（**推荐升级路径**）

上面的 `continentality ∈ [0,1]` 是**工程近似**。气候学里有**成型的、经过数值验证的**
大陆度指数，它们把「振幅 A（年较差，°C）」和「纬度 θ（度）」组合成一个无量纲百分比，
**正好是我们需要的那个量**。四个主流指数的公式与系数如下
（全部逐个对照原文表格复算过，置信度**高**）：

来源：Vilček, Škvarenina, Vido, Nalevanková, Kandrík & Škvareninová (2016),
*Earth Syst. Dynam.* **7**:735–744,
[esd-7-735-2016](https://esd.copernicus.org/articles/7/735/2016/esd-7-735-2016.html)（开放获取）。

| 指数 | 公式 | 数值验证 | 分级 |
| --- | --- | --- | --- |
| **Gorczynski (1920/22)** | `K_G = 1.7·(A / sin θ) − 20.4` | Hurbanovo 算得 33.0，原文印 33.0；Michalovce 34.3 vs 34.2 | 0–33 过渡海洋性；34–66 大陆性；67–100 极端大陆性。适用约 30–60°N；海洋性地区会给负值 |
| **Conrad** | **`K_C = 1.7·A / sin(θ + 10°) − 14`** | Hurbanovo 32.8 vs 32.8；Michalovce 34.1 vs 34.0 | −20~20 超海洋性；20–50 海洋性；50–60 亚大陆性；60–80 大陆性；80–120 极端大陆性 |
| **Ivanov (1959)** | `K_I = 100·A / (0.33·θ)` | Oravská Lesná 132.6 vs 132.8 | <47 极海洋性 … >214 极大陆性（10 级） |
| **Khromov (1957)** | `K_Kh = 100·(A − 5.4·sin θ) / A` | Hurbanovo 82.8 vs 82.7；Michalovce 83.2 vs 83.0 | 原文称「`5.4·sin θ` 应表达纯海洋性气候的年较差」 |

> ⚠️ **Conrad 的公式极易写错**：**分母是 `sin(θ + 10°)`，不是 `sin θ`**。
> 用 `sin θ` 会得到与原文表格完全不符（且可能为负）的结果。
> Conrad 自己是为了消除 θ→0 处的奇点才给纬度加了 10°。
> Gorczynski 的常数 1.7 则源自「假设东西伯利亚的 Verchojansk 代表 100% 大陆度」。

**用法**：把 `continentality` 定义成 `K` 归一化后的值，就能省掉主观查表：

```
// 取 Gorczynski（验证最充分、分级最常用）
A_annual = 2 * A(lat)                       // 年较差 = 2 × 振幅
K_G      = 1.7 * (A_annual / sin(latRad)) - 20.4     // [%]，仅对 30–60° 纬度有效
continentality01 = clamp(K_G / 100, 0, 1)

// 或者反过来：已知 continentality -> 直接得振幅，跳过 §2.1.1 的查表
//   A_annual = (K_G + 20.4) * sin(latRad) / 1.7
//   A        = A_annual / 2
```

**为什么这比查表好**：Fargo ND（46.9°N）年较差 **34.2 K**，Seattle WA（47.5°N）**14.1 K** ——
**几乎同纬度，相差 2.4 倍**（NOAA 1991–2020 站点常态，本调研交叉验证）。
任何只依赖纬度的振幅表都必然在其中一端错 10 K 以上。
大陆度指数把「振幅」本身当作可观测量，是**自洽**的。

> 本项目的 ERA5 实测也独立复现了同一现象：Miami（25.8°N）振幅 3.5 K
> vs Riyadh（24.7°N）11.3 K。
> **注意两个数据源有系统差**：NOAA 站点常态给出的振幅普遍**大于**我的 ERA5 拟合
> （如 Fargo 17.1 vs 同纬度带 ERA5 值更低），这与 §2.3.3 讨论的网格平滑效应一致。

#### 方案 D：直接用「纬度 + 距海岸距离」拟合振幅 —— **已实测拟合并交叉验证（推荐）**

方案 C 的大陆度指数需要一个输入 `A`（年较差），而这正是我们要预测的量 ——
**在离线场景下它是循环论证**。本节补上真正闭环的方案：
用「距最近海洋的距离 `d`」直接预测 `A`，**不需要任何气候数据**。

**做法**：取 46 个全球测站（经纬度已知），
① 用 ERA5 2015–2024 逐日均温做一阶谐波拟合得到**实测** `A`；
② 用 1 km 全球陆海掩膜做径向搜索，得到每站的 `d`；
③ 拟合 `A = f(|lat|, d)` 并用**留一交叉验证（LOO）**评估。

**推荐公式（可直接实现）**：

```
sat(d) = d / (d + 400)                      // d 单位 km；饱和函数，0=紧邻海岸，→1=深内陆
A(lat, d) = sin(|lat|) · ( 9.1 + 18.1 · sat(d) )      // 单位 K
```

**两条独立推导路线给出几乎相同的系数 —— 这是最强的一条互证**：

| 路线 | a | b | 说明 |
| --- | --- | --- | --- |
| **① 直接最小二乘**拟合 `A` | 9.17 | 18.32 | 纯数据驱动 |
| **② Gorczynski 反演**（先用实测 `A` 算已验证的大陆度指数 `K_G`，再拟合 `K_G = f(d)`，最后反解回 `A`） | 9.07 | 18.10 | 经由**独立验证过**的气候学指数 |

`K_G = 10.45 + 61.55·sat(d)`（n=37，`|lat|` 20–66°，R² = 0.674），
**corr(sat(d), K_G) = +0.821**。
两条路线系数差 <0.25 K，**说明这不只是曲线拟合，而是有气候学意义的**。

**精度（46 站，留一交叉验证）**：

| 模型 | 留一 LOO RMSE | 留一 LOO MAE | 样本内 R² |
| --- | --- | --- | --- |
| 无预测量（取平均） | 6.24 K | 5.15 K | — |
| **只用纬度** `A ~ sin|lat|` | **4.45 K** | 3.43 K | 0.528 |
| **纬度 + 距海岸距离**（本方案） | **2.47 – 2.66 K** | **1.71 – 1.82 K** | **0.843** |

→ **加入距海岸距离把振幅误差降低约 40%**（4.45 K → 2.5 K）。
这直接把 §2.1.1 里「振幅只能靠 R²=0.60 的纬度回归」这个最大误差源
从 ±5 K 量级压到 **±2.5 K 量级**。

| --- | --- | --- | --- | --- | --- | --- |

| 10–20° | 2.5 | 3.1 | 4.1 | 5.2 | 6.0 | 6.6 |
| 20–30° | 4.2 | 5.0 | 6.6 | 8.4 | 9.9 | 10.8 |
| 30–40° | 5.6 | 6.8 | 9.0 | 11.4 | 13.4 | 14.7 |

**两个有用的否定结果（都做了检验，结论是「不要加」）**：

1. **海拔没有帮助**。加入 `elev_km` 项后留一 RMSE 从 2.66 K 变成 2.68 K —— **变差了**。
   原因是高海拔站点（Denver / Almaty / Ulaanbaatar）同时也很内陆，
   海拔项与距海岸距离**共线**，拟合出的系数甚至是负的（物理上说不通）。
   **结论：只用 `|lat|` 与 `d` 两个变量，不要加海拔。**
2. **海岸方位（东岸/西岸）没有帮助**。物理上应该有 ——
   西风带把海洋空气从**西**边带来，所以西岸海洋性、东岸受大陆气团影响。
   实测上东岸站点残差平均 +0.96 K、西岸 −1.09 K（系统性差 2.05 K，确实存在），
   但把「最近海洋位于西侧」当作回归变量后，**留一 RMSE 从 2.63 K 只降到 2.59 K**，
   且**没有修正任何一个具体的坏样本**（Tokyo / Halifax 误差纹丝不动）。
   原因：径向搜索找到的「最近海洋方位」反映的是**局地海岸几何**（海湾、半岛），
   不是**大陆尺度的海陆分布**。
   **结论：不要引入这个变量 —— 它增加复杂度但没有收益。**

**残差结构（诚实披露，这些是模型的已知边界）**：

| 站点 | 观测 A | 预测 A | 误差 | 原因 |
| --- | --- | --- | --- | --- |
| **Yakutsk** | 28.7 | 18.6 | **+10.0** | 西伯利亚冷极，极端大陆性远超 `d=750 km` 所暗示的程度 |
| Tokyo | 11.2 | 5.6 | +5.6 | **东岸**：沿海但冬季受大陆冷气团控制 |
| Halifax | 11.2 | 6.8 | +4.5 | 同上（加拿大东岸） |
| Riyadh | 11.3 | 7.5 | +3.8 | 沙漠内陆，`d=370 km` 低估了其大陆性 |
| Brasilia | 1.4 | 5.9 | −4.5 | 热带高原：低纬处大陆度指数失效（模型高估） |
| Moscow | 13.5 | 16.9 | −3.4 | 西欧西风调节，`d=640 km` 高估了其大陆性 |

> **误差上界的现实预期**：多数站点在 ±2 K 内，但**极端大陆性（东西伯利亚/加拿大内陆）
> 与低纬高原是系统性失效区**，单项误差可达 5–10 K。
> 如果模组要在西伯利亚/加拿大内陆准确，仍需 `ClimateResolver` 覆盖接口。

**重量级：陆海掩膜可以非常小**。`sat(d)` 在 `d ≫ 400 km` 之后是平的，
所以掩膜**只需要区分「沿海」与「内陆」**，不需要精确海岸线。实测（以 1 km 掩膜为基准）：

| 掩膜分辨率 | 网格数 | 打包体积 | 平均 \|ΔA\| | 最大 \|ΔA\| |
| --- | --- | --- | --- | --- |
| 5° | 36 × 72 = 2,592 | **324 B** | 0.81 K | 4.49 K |
| **2°** | 90 × 180 = 16,200 | **2.0 kB** | 0.42 K | 1.70 K |
| 1° | 180 × 360 = 64,800 | 8.1 kB | 0.35 K | 1.48 K |
| 0.5° | 360 × 720 = 259,200 | 32.4 kB | 0.19 K | 0.56 K |

→ **推荐 2° 掩膜（约 2 kB，按位打包；即使每格 1 字节也才 16 kB）**：
退化不超过 1.7 K，完全可以随 jar 附带，符合「离线保持轻量」的约束。
**这比方案 C 更轻**——方案 C 需要年较差数据，方案 D 只需要一张 2 kB 的位图。

#### `d`（距海岸距离）的**精确可复算定义** —— 单元测试请以本节为准

> 这一节是**规范性**的：交付的掩码文件、CSV 标定表与全部系数都以下面这个定义为准。
> 实现与测试必须与此逐条一致，否则系数不成立。

**D1. 输入**：查询点 `(lat, lon)`，以及已加载的位掩码 `land[r][c]`（`true` = 陆地）。

**D2. 格归属**（行 0 在最北）：

```
row = clamp( floor( (90.0 - lat) / cellDegrees ), 0, nlat-1 )
col = clamp( floor( ( ( (lon + 180.0) mod 360 ) + 360 ) mod 360 / cellDegrees ), 0, nlon-1 )
isOcean(lat, lon) = !land[row][col]
```

**D3. 距离是「到大圆上探针点落入的海洋格」，不是「到海洋格中心」**。
这一点**必须**说清楚，因为它直接决定系数：

- 若定义成「到最近海洋格**中心**的大圆距离」，那么一个真正临海的城市
  （真实离海 10 km）会得到 `d ≈ 111 km`（1° 格）甚至 `222 km`（2° 格），
  因为最近的海洋格中心就在邻格中央。
  `sat(111)=0.217` vs `sat(10)=0.024`，在纬度 45° 处会造成
  `sin45°·18.1·0.193 ≈ 2.5 K` 的系统性高估。
- 因此本定义采用**沿大圆逐步外推、一旦探针点落入海洋格即停止**的方式，
  等价于「到海洋格**边缘**」的距离（误差不超过一个步长）。

**D4. 径向搜索参数**（全部为规范值）：

```
步长  STEP_KM  = 25.0 km
方位数 NAZ     = 72          // 即 0°, 5°, 10°, ..., 355°
半径上限 MAX_KM = 2500.0 km
```

**D5. 算法**（环形外推，与「逐方位求最小」等价）：

```
function distToCoastKm(lat, lon):
    if isOcean(lat, lon): return 0.0
    for r = STEP_KM, 2*STEP_KM, ..., MAX_KM:
        for k = 0 .. NAZ-1:
            θ = 360° * k / NAZ
            (plat, plon) = greatCircleDestination(lat, lon, θ, r)
            if isOcean(plat, plon): return r
    return MAX_KM                       // 到上限仍无海洋 -> 取上限值
```

**D6. 大圆公式**（球面，`R = 6371.0088 km`，WGS84 平均半径）：

```
δ = r / R
φ2 = asin( sin φ1 · cos δ + cos φ1 · sin δ · cos θ )
λ2 = λ1 + atan2( sin θ · sin δ · cos φ1 , cos δ − sin φ1 · sin φ2 )
（结果经度归一化到 [−180, 180)）
```

**D7. 极区经度收敛的处理 —— 本定义天然没有这个问题**。
这是本节最容易被做错的一点：

- **不要**在「经纬度索引网格」上做搜索（例如 `for dlat in …: for dlon in …: 用经纬度差算距离`）。
  那样在纬度 80° 处，1° 经度只有约 19 km，而 1° 纬度有 111 km ——
  会**严重高估**高纬地区的 `d`（一个「经度上差 10 格」的海洋在 80°N 其实只有 ~190 km 远）。
- 本定义**沿真实大圆按公里步进**（D6），每一步都是地面上的等距圆环，
  与经线收敛无关；且 `isOcean` 用 D2 的 `floor` 查格，
  高纬处 1° 经度对应的格变窄这件事已经被 `floor` 正确吸收。
  **因此从赤道到极点，`d` 的定义保持一致，无需任何纬度修正。**

**D8. 陆/海判定阈值**：先栅格化到 **0.25° 陆地占比网格**
（每格 4×4 = 16 个子采样点，用点在多边形内判定），
再把 `k×k` 个 0.25° 格求平均得到目标分辨率格的陆地占比，
**占比 ≥ 0.5 记为陆地，否则记为海洋（平局归海洋）**。

**D9. 冰盖处理 —— 南极与格陵兰都算「陆地」**（两者一致，已实测确认）：

| 位置 | 1 km 参考 | 2° 掩膜 | 1° 掩膜 |
| --- | --- | --- | --- |
| 南极 (−75, 0) / (−80, 90) / (−70, 45) | 陆地 | 陆地 | 陆地 |
| 格陵兰 (72,−40) / (65,−45) / (78,−35) | 陆地 | 陆地 | 陆地 |

理由：它们对海洋性气团是**实体屏障**，作为「陆地」参与 `d` 计算在物理上正确。
**南极内陆的 `d` 因此会取到上限 2500 km**，对应 `sat = 0.86`，
这是有意为之（南极内陆确实是地球上最大陆性的地方）。

**D10. 量程与实测范围**：`d` 被量化到 25 km 的整数倍。
46 个标定站的实测范围是 **0 – 1925 km**，
**没有任何站点触及 2500 km 上限**，所以上限的选择不影响标定结果。

**实现**：

```java
// 交付的掩码（见下面「交付物」）：
//   1° : /data/nowweather/geo/landmask1deg.bin   (8,100 B, 推荐)
//   2° : /data/nowweather/geo/landmask2.json     (3,476 B, 自描述 base64)
static final double STEP_KM = 25.0, MAX_KM = 2500.0;
static final int NAZ = 72;
static final double R_EARTH = 6371.0088;

double distToCoastKm(double lat, double lon) {
    if (isOcean(lat, lon)) return 0.0;
    double p1 = Math.toRadians(lat), l1 = Math.toRadians(lon);
    for (double r = STEP_KM; r <= MAX_KM; r += STEP_KM) {
        double d = r / R_EARTH;
        for (int k = 0; k < NAZ; k++) {
            double b = Math.toRadians(360.0 * k / NAZ);
            double p2 = Math.asin(Math.sin(p1)*Math.cos(d)
                                + Math.cos(p1)*Math.sin(d)*Math.cos(b));
            double l2 = l1 + Math.atan2(Math.sin(b)*Math.sin(d)*Math.cos(p1),
                                        Math.cos(d) - Math.sin(p1)*Math.sin(p2));
            double plat = Math.toDegrees(p2);
            double plon = (Math.toDegrees(l2) + 540.0) % 360.0 - 180.0;
            if (isOcean(plat, plon)) return r;
        }
    }
    return MAX_KM;
}

/** 季节性振幅（K）；本函数替代 §2.1.1 的纬度查表法 */
double annualAmplitudeK(double latDeg, double distToCoastKm) {
    double sat = distToCoastKm / (distToCoastKm + 400.0);
    return Math.sin(Math.toRadians(Math.abs(latDeg))) * (9.1 + 18.1 * sat);
}
```

> 搜索成本：最坏 `100 环 × 72 方位 = 7,200` 次查表，**每个地点只算一次并缓存**
> （§7.1 建议把 `distToCoastKm` 一并缓存）。内陆点会一直跑到上限，
> 但真实取值 ≤ ~1925 km，可把上限降到 2000 km 省 20% 时间而不改变任何标定站的结果。

| 掩膜 | 文件体积 | 平均 \|ΔA\| | **最大 \|ΔA\|** | 最大误差出现在 |
| --- | --- | --- | --- | --- |

> 与需求的「≤8 kB、误差 ≤1.7 K」**基本吻合**（最坏值超出 0.08 K，在噪声范围内）。

## 3. 天气状态（晴/云/雨/雪）的推算

### 3.1 降水形态（雨 / 雪 / 雨夹雪）

#### 核心事实：**阈值不是 0 °C**

| 来源 | 50% 雪/雨 温度（干球 2 m） | 过渡带 | 置信度 |
| --- | --- | --- | --- |
| **[Dai (2008), *GRL* 35, L12802](https://doi.org/10.1029/2008GL033295)** | 陆地 **1.2 °C**；海洋 **1.9 °C** | 陆地 **−2 ~ +4 °C**；海洋 −3 ~ +6 °C | **高** |
| **[Jennings et al. (2018), *Nat. Commun.* 9:1148](https://doi.org/10.1038/s41467-018-03629-7)**（1780 万次观测，29 年） | 北半球平均 **1.0 °C**，95% 测站落在 **−0.4 ~ +2.4 °C** | — | **高** |
| **[HESS 2019, doi:10.5194/hess-23-3765-2019](https://doi.org/10.5194/hess-23-3765-2019)** 表 2（归纳实用阈值） | 常用 0/1/2/3 °C；区间 (−0.5,+0.5)；**USACE (1956) *Snow Hydrology* 的经典区间 (−1.0, +3.0) °C** | — | **高** |
| Steinacker (1983)（因斯布鲁克 1977–82 实测） | **50% 雪在湿球 0.5 °C / 干球 1.0 °C**；**50% 雨在湿球 1.2 °C / 干球 1.8 °C** | 雨夹雪占湿球 0–2 °C；**湿球 >2.5 °C 无雪**；干球雪可到 6 °C（极端干燥下 16 °C） | 中高 |
| Auer (1974)（美国中部约 1000 次观测，大平原干燥） | 干球约 **2.5 °C** | 与 Innsbruck 的 ~1.4 °C 之差被归因于大平原湿度远低 | 中高 |
| SNOWPACK 模式默认值 | **1.2 °C** | — | 高 |
| **HESS 2019 归纳的实用阈值** | 干球 **0/1/2/3 °C**；**露点 0/1 °C**；**湿球 0/1 °C** | 全雪/全雨区间 **(−1, +3) °C** | **高** |
| **NWS 业务判据**（[weather.gov/ama/winterpreciptypes](https://www.weather.gov/ama/winterpreciptypes)） | 地面 T ≤ 0 °C，或浅融化层且最高 <1 °C，或湿球零度高度 <1500 ft | 融化层 1–3 °C → 雨夹雪；>3 °C → 冻雨 | **高** |

> ⚠️ **对需求里两条前提的更正**（本次调研专门核了这两条）：
> 1. 流传的「**NWS 业务阈值约 1.5 °C 或 2.2 °C**」**无法追溯到任何 NWS 官方来源**。
>    NWS 的实际判据是上面的融化层/湿球零度高度规则，**不是单一 2 m 阈值**。
> 2. Auer (1974) 常被引用为 **2.2 °C**，但可核实的人形图读数是 **约 2.5 °C**。
>
> **这两个数字都不要当真值引用。** 同理「**Steinacker (1992)**」这篇文献**不存在**——
> 有可用数值的是 **Steinacker (1983)**。若见人引用 1992 版，那是张冠李戴。

**为什么必须用非零阈值（有量化依据）**：
Rajagopal & Harpold (2016), *JAWRA* 52:1142–1154,
[doi:10.1111/1752-1688.12443](https://doi.org/10.1111/1752-1688.12443) 实测：
**「把温度阈值最优化后，相态预测比用 0 °C 阈值改善了 34%；再按测站海拔建立阈值又改善 12%。」**
且 HESS 2019 的误差排名中，**最差的四个方法正是平坦 0 °C 与平坦 2–3 °C**。

**需要哪些预报量（决定我们的降级策略是否成立）**：
Froidurot et al. (2014), *J. Hydrometeorol.* 15:685–696,
[doi:10.1175/JHM-D-13-073.1](https://doi.org/10.1175/JHM-D-13-073.1) 用瑞士 30 年资料得出：
**「与地面变量不同，由大气廓线导出的变量（如垂直温度梯度）几乎不能改善地面相态判别。
在所有被检验的变量中，地面气温与相对湿度具有最强的解释力。」**
→ **这正好为我们的方案背书**：只需要 `T` + `RH`（即湿球），
**不需要**气压廓线或任何垂直结构数据 —— 对一个天气模组这是关键的可行性结论。

**阈值的地理变化（不可忽略）**：HESS 2019 指出 50% 阈值
**从太平洋沿岸的约 1 °C 升到落基山脉的 3 °C 以上**；
该研究在其站点上拟合的最优阈值分别是 **1.0 / 2.0 / 3.0 °C**（暖海洋性 / 过渡 / 冷大陆性）。

**本项目推荐采用（可直接实现）**：

```
// 干球阈值 —— 先用这一版，简单且与 Dai/Jennings 一致
rainSnowThresholdC = 1.2      // 50% 概率点（Dai 2008 陆地值，SNOWPACK 默认值）
transitionHalfWidthC = 2.5    // -> 过渡带 −1.3 ~ +3.7 °C，覆盖 USACE (−1,+3) 与 Jennings 95% 区间

if      T >= threshold + halfWidth   -> RAIN          // T >= 3.7 °C
else if T <= threshold - halfWidth   -> SNOW          // T <= −1.3 °C
else {                                 // 过渡带：概率化
    pSnow = 0.5 * (1 - (T - threshold) / halfWidth)   // 线性；T=1.2 -> 0.5
    // 用确定性或随机：见下方「形态判定」
}
```

#### 湿球温度比干球更准（有文献支撑，置信度高）

多篇研究一致表明**湿球温度（wet-bulb）优于 2 m 干球温度**：

- Wang, Broxton & Fang (2019), *GRL* 46, [doi:10.1029/2019GL085722](https://doi.org/10.1029/2019GL085722)
- Harder & Pomeroy (2013), [doi:10.1002/hyp.9799](https://doi.org/10.1002/hyp.9799)
- Sims & Liu (2015), [doi:10.1175/JHM-D-14-0211.1](https://doi.org/10.1175/JHM-D-14-0211.1)
- Jennings et al. (2018)：**「依赖湿度的方法在 RH<100% 且温度在 0.6–3.4 °C 时明显优于只用气温的方法」**

极强的量化例子（Sims & Liu 2015，原文）：**「在近地面湿球温度为 0 °C 时，
垂直温度递减率 6 °C/km 给出 86% 的固态降水条件概率，而递减率 −2 °C/km 只给出 45%。」**
这说明**递减率与相态判定是耦合的**。（同一研究还发现：**土地覆盖类型不影响降水相态**，
地面气压仅个别情形有意义 —— 这两条对我们是好消息，可以不管群系类型。）

**实现湿球温度**（Stull 2011 经验式，只需 T 和 RH，**无需迭代**）【工程近似，但系数来自文献】：

```
// Stull, R. (2011), "Wet-Bulb Temperature from Relative Humidity and Air Temperature",
// J. Appl. Meteor. Climatol. 50(11):2267-2269. 有效范围 RH 5~99%, T −20~50 °C
Tw = T * atan(0.151977 * sqrt(RH + 8.313659))
   + atan(T + RH)
   - atan(RH - 1.676331)
   + 0.00391838 * pow(RH, 1.5) * atan(0.023101 * RH)
   - 4.686035
// T [°C], RH [%], Tw [°C]
```

把 `T` 换成 `Tw`、阈值换成 **0.5 °C**（Steinacker 1983 的 50% 雪点），即得湿球版判据：

```
Tw_threshold = 0.5          // Steinacker 1983；HESS 2019 归纳的实用湿球阈值是 0 与 1 °C，
                            // 0.5 落在两者之间，取谁都合理 —— 但要固定一个并注明来源
if      Tw >= Tw_threshold + 2.0 -> RAIN
else if Tw <= Tw_threshold - 2.0 -> SNOW
else -> 过渡带（雨夹雪 / 概率化）
```

> **实测阈值汇总（湿球）**：Steinacker (1983) 50% 雪在 **0.5 °C**、50% 雨在 **1.2 °C**、
> 雨夹雪占 **0–2 °C**、**>2.5 °C 无雪**。HESS 2019 归纳在用的湿球阈值是 **0 °C 与 1 °C**。
> 所以「0.5 °C」是一个合理的中点选择，但**不是唯一权威值**，差异约 ±0.5 °C。

**工程建议**：
- 有湿度数据（`bio.humidity` 或上次观测的 `humidityPercent`）→ **用湿球版**（更准，尤其能正确处理
  「干燥空气里 +3 °C 下雪」这一真实但反直觉的现象：RH=54%、T=+3 °C 时 Td=−6 °C，湿球在冰点以下）；
- 没有湿度 → 用干球版，阈值 1.2 °C。
- **落到 Minecraft 时还必须过 `docs/BIOME_CLIMATE.md` 的白名单**：
  沙漠 `precipitation = NONE` 时禁止一切降水；群系温度范围不含雪温时把雪改成雨。
  这正是原版 [MC-259935](https://mojira.dev/MC-259935)
  「`Biome#doesNotSnow()` 只看温度、不看降水标志，导致 NONE 群系也积雪」的同类问题
  —— 25w31a 已修，但**季节/天气模组在旧版本上会放大它**，所以我们要自己在应用层挡住。

### 3.2 降水概率：由季节 + 纬度 + 生物群系湿度近似

#### ❗ 重要否定结论：**不存在「湿度 → 降水概率」的可靠闭式公式**

这是本次调研最有用的一条**负面**发现。所有经典天气发生器
（Richardson 1981 WGEN、CLIGEN、GWGEN、LARS-WG、WeaGETS）**全部**从
**月气候统计量**生成降水，**没有一个**用「相对湿度」映射到降水概率。
试图构造 `P(降水) = f(RH, T)` 的一手来源也没找到（GCM 里的 critical relative humidity
方案阈值常引 0.7–0.9，但**具体系数未能核实**）。置信度：**高**（这是「检索不到」的结论，非「查到低质量来源」）。

**所以不要发明 `P(precip) = f(RH, T)`。** 正确做法是马尔可夫链 + 月气候态。

#### 方案：一阶两状态马尔可夫链（WGEN/Richardson 骨架，置信度：高）

这是气象发生器 40 多年的标准做法，源码级可查。

```
月参数（每个月一对）：
    P(W|W)  —— 昨天湿、今天也湿的概率
    P(W|D)  —— 昨天干、今天湿的概率

每日生成：
    u = uniform(0,1)
    if (昨天是湿日)  今天湿 ⇔ u <= P(W|W)
    else             今天湿 ⇔ u <= P(W|D)
```

（[CLIGEN 源码](https://infosys.ars.usda.gov/svn/code/third_party/climate/cli_gen/cligen.src/cligen.for)，置信度**高**）**完全一致**。

#### 用「气候大类 + 湿度」近似 P(W|W) / P(W|D) —— 无月气候数据时的降级

如果拿不到逐月气候态，用生物群系字段近似**【工程近似，低置信度】**：

```
// 先由生物群系得到「气候湿润度」 hum ∈ [0,1]
hum = bio.humidity

// 年湿日比例（由本实测表内插：RH 26% -> 4%, RH 86% -> 82%）
wetDayFraction = clamp(1.15 * hum - 0.30, 0.01, 0.95)

// 转移概率：用本实测表的趋势线性近似
// P(W|W) 从干旱 0.15 到极湿 0.88；P(W|D) 从 0.02 到 0.57
P_WW = clamp(0.15 + 0.73 * hum, 0.10, 0.90)
P_WD = clamp(-0.05 + 0.72 * hum, 0.01, 0.65)

// 若两者算出的稳态比例与 wetDayFraction 矛盾，用 wetDayFraction 反解 P_WD：
//   P_WD = wetDayFraction * (1 - P_WW) / (1 - wetDayFraction)
P_WD = wetDayFraction * (1 - P_WW) / max(1e-6, 1 - wetDayFraction)
```

1. **持续性的有效期只有约 1–2 天**。
   纯持续性在 **h=1 时优于气候态 25%**，**h=2 时已打平**，**h≥3 起就比气候态更差**
   （h=30 时差 37%）。这与 Stull 说的「持续性只够约 2 天」**独立吻合**。
2. **最优权重 w(h) 有干净的闭式形式**（本项目拟合，SSE=0.002，**极好**）：

   ```
   w(h) = 1 / (1 + (h / 2.10)^1.20)          h 单位为小时/24 = 天
   ```

   校验：`h=1→0.71`（实测 0.73）、`h=2→0.51`（0.50）、`h=3→0.39`（0.37）、

   > 另一候选形式 `w = exp(-(h/3.15)^0.52)`（拉伸指数）SSE=0.106，**明显更差**。
   > 用有理式。
   > ⚠️ **但注意：`w(h)` 是在「只有一次观测」的前提下最优的。** 它同时是
   > **缓存过期策略的直接依据**（见 §7）。

3. **气候态的 RMSE 就是离线推算的温度误差下限**：中纬度约 **3.2–3.4 K**，
   本实测的站间范围是 **0.74 K（Singapore）~ 5.05 K（Yakutsk）**。
   这是**逐日均温**的谐波残差；逐日 Tmax/Tmin 的气候态 RMSE 更大（3.2 K 均值）。
   **任何离线模型都不可能显著优于这个数**，因为它在定义上就等于「不利用任何当日信息」。

## 4. 风的推算

### 4.1 由纬度带近似风向

**全球行星风带**（置信度：**高**，教科书级）：

| 纬度带 | 名称 | 北半球风向 | 南半球风向 |
| --- | --- | --- | --- |
| 0°–30° | **信风带**（trade winds / Hadley cell 近地面） | **东北风 (NE)** | **东南风 (SE)** |
| 30°–60° | **西风带**（westerlies / Ferrel cell） | **西南风 (SW)** | **西北风 (NW)** |
| 60°–90° | **极地东风带**（polar easterlies） | **东北风 (NE)** | **东南风 (SE)** |
| 约 30° | 副热带高压（马纬度）—— **静风带** | 弱/多变 | 弱/多变 |
| 约 0° / 60° | 赤道低压带 / 极锋 —— 辐合带 | 弱/多变 | 弱/多变 |

> ⚠️ **纬度边界有两套并存的说法，差异可达 10°**，实现时要注明用哪套：
> - **Stull（*Practical Meteorology* Ch.11）**：0–30 / 30–60 / 60–90 —— 上表用的这套；
> - **英国气象局（按环流胞分）**：Hadley 胞「从赤道到约 **30–40°**」，
>   Ferrel 胞「**30–40° 到 60–70°**」，极地胞「**60–70° 到极点**」；
> - **NOAA** 则把信风描述为**一条 60° 宽的整体带（30°N–30°S）**，
>   而赤道辐合带/赤道无风带是 **10° 宽（5°N–5°S）**。
>
> 三套都对，只是切分口径不同。**不要声称只有一套正确。**（置信度：**高**）

**可实现的简化公式**【工程近似】：

```
windDirDeg(lat) =
    if absLat < 5:        UNDEFINED          // 赤道辐合带（5°N–5°S），静风/多变
    if absLat < 30:       NORTH ?  45 : 135  // NE / SE（以「风从哪来」记 → 见下）
    if absLat < 60:       NORTH ? 225 : 315  // SW / NW
    else:                 NORTH ?  45 : 135  // NE / SE

// 季节位移：风带随 ITCZ 南北摆动
seasonalShiftDeg = 13 * sin(2π * (dayOfYear - peakDay) / 365.25)
finalDirDeg = (windDirDeg + seasonalShiftDeg) mod 360
```

**季节位移幅度用 13° 是有依据的**（原为 10°，现按文献上调；置信度**高**）：

| 量 | 实测值 | 来源 |
| --- | --- | --- |
| ITCZ 纬向平均季节性移动范围 | **12.5°**（冬季 5.3°S ↔ 夏季 7.2°N，年均 1.65°N） | Donohoe et al. (2013), *J. Climate* 26, [doi:10.1175/JCLI-D-12-00467.1](https://doi.org/10.1175/JCLI-D-12-00467.1) |
| ITCZ 季节范围（Stull 口径） | JJA 中心约 **9°N**，DJFM 约 **6°S**（≈15°）；且**明显不跟随太阳赤纬到满量程** | Stull Ch.11 |
| ITCZ 陆地放大（非洲） | 最南约 **14°S**、最北约 **9°N**（≈**23°**，比海洋大一倍） | Liu et al. (2020), *ERL* 15:104011, [doi:10.1088/1748-9326/aba033](https://doi.org/10.1088/1748-9326/aba033) |
| 副热带高压（南大西洋）纬向移动 | **仅约 3.8°**（3 月 32.5°S ↔ 8 月 28.7°S） | Reboita et al. (2019), *Front. Earth Sci.* 7:8, [doi:10.3389/feart.2019.00008](https://doi.org/10.3389/feart.2019.00008) |

> 取 **13°** 是海洋尺度的折中；若知道该地在非洲/大型大陆内部，可取 **20–23°**；
> 副热带高压带的移动远小于信风带（约 4°），所以**不要对整条风向带施加同一个位移**。
> 上述位移适用于「某地气候态风向的年变化」这一粗糙用途；
> 更精细的做法是让位移量随 `absLat` 变化。

**风向约定（务必明确，否则会拧反）**：气象上「风向」指**风从哪里来**。
所以北半球信风「东北风」= 从东北吹向西南 = 矢量方位角 **225°**（若用「吹向」记法）。
本项目建议统一采用**「来向」**（与 Open-Meteo `wind_direction_10m_dominant`
及 `WeatherObservation.WindDirection` 一致），即 **NE = 45°**。上面公式已按「来向」写。

### 4.2 由季节近似风速

行星风带的风速随季节变化：**冬季风带增强**（经向温度梯度大），夏季减弱。
另外**副热带高压带与赤道辐合带是弱风带**。

#### 先给定标尺：地表风速到底是多少（**实测值，置信度：高**）

这一次调研把风速的**绝对标定**补齐了，所以 §4.2 的速度值**不再是无依据的占位值**：

| 量 | 实测值 | 来源 |
| --- | --- | --- |
| **全球平均地表风速** | **5.85 m/s**（= 21.1 km/h） | Lauscher (1951), *Arch. Meteorol. Geophys. Bioklimatol. B* **2**:427–440, [doi:10.1007/BF02242696](https://doi.org/10.1007/BF02242696) |
| **全球平均 10 m 风速：陆地 / 海洋** | **3.28 / 6.64 m/s**（= **11.8 / 23.9 km/h**）；80 m 处 4.54 / 8.60 m/s | Archer & Jacobson (2005), [doi:10.1029/2004JD005462](https://doi.org/10.1029/2004JD005462) |
| **信风带**（纬向平均） | **≈ 7 m/s**（= 25.2 km/h） | Stull Ch.11 p.330 原文 |
| **南半球西风带（咆哮西风带）** | **8–12 m/s（15–24 kt），最强在 45–55°S** | Univ. Oldenburg SEOS（**中**）；Lauscher (1951) 独立给出南半球西风带全年 **>10 m/s**（**高**） |
| 极地东风带平均风速 | **未找到** —— Stull 只称其为「一条弱东风带」 | — |
| 参考极端值 | Cape Denison（南极 Adélie Land）年均 **≈20 m/s**，是「地表附近观测到的最强风」 | Wendler et al. (1997), [doi:10.1029/96JD03438](https://doi.org/10.1029/96JD03438) |

**由此可以得到一个可辩护的换算**：实测的**陆/海比 = 3.28 / 6.64 = 0.494**。
把风带的纬向平均值乘上这个比值，就得到陆地 10 m 的合理估计：

```
// 陆地 10 m 估计 = 纬向(海洋性)实测值 × 0.494
信风带        : 25.2 × 0.494 ≈ 12.4 km/h
西风带(南半球): 28.8–43.2 × 0.494 ≈ 14.2–21.4 km/h
```

**这恰好落在本文档原先填的 14 / 18 km/h 区间内** ——
所以 §4.2 的数值从「无依据占位」升级为「由实测陆/海比换算得到的**派生值**（置信度：中）」。

**简化公式**【派生值 + 工程近似】：

```
baseSpeedKmh(absLat) =
    // 基础值：风带纬向实测值 × 陆海比 0.494（Archer & Jacobson 2005）
    if absLat < 5:    7      // 赤道辐合带，弱风
    if absLat < 30:  13      // 信风带（实测 ~7 m/s 纬向 × 0.494）
    if absLat < 32:   8      // 副热带高压，弱风（马纬度）
    if absLat < 60:  18      // 西风带（实测 8–12 m/s × 0.494，取中偏低）
    else:            12      // 极地东风带（无实测，纯工程值 ⚠）

// 季节性增强：冬半年更强
seasonalFactor = 1 + 0.25 * (-cos(2π * (dayOfYear - peakDay) / 365.25))
                 // 峰值日在夏季 -> 冬半年 = factor 1.25，夏半年 = 0.75

// 生物群系风力度调制（0~1，来自 docs/BIOME_CLIMATE.md）
bioFactor = 0.6 + 0.8 * bio.windiness

speedKmh = baseSpeedKmh * seasonalFactor * bioFactor
```

> ⚠️ **极地东风带的 12 km/h 仍然是纯工程值** —— 本次调研**找不到**该风带的平均风速实测。
> Stull 只说它「弱」。若要改进，需接入 §8.3 的 CLIGEN `.PAR` 风统计。
> `seasonalFactor` 的 ±25% 也无文献支撑（定性方向「冬季更强」是对的）。

**文献对照（置信度：高）**：地表风速的统计分布通常用 **Weibull 分布**描述
（[HOMER Pro 文档](https://homerenergy.com/products/pro/docs/latest/weibull_distribution.html)、
[\(k\) 参数说明](https://homerenergy.com/products/pro/docs/latest/weibull_k_value.html)）：

```
f(v) = (k/c)·(v/c)^(k−1)·exp(−(v/c)^k)
v̄ = c·Γ(1 + 1/k)
```

| 场所 | 形状参数 k |
| --- | --- |
| 典型范围 | **1.5 – 2.5** |
| 合成默认 | **k = 2**（= Rayleigh 分布） |
| 阵风大 | **k ≈ 1.5**（分布宽） |
| **稳定的信风环境** | **k = 3–4**（分布窄） |

**k=2（Rayleigh）时有简洁形式**：`c = v̄ / Γ(1.5) = v̄ / 0.8862 = 1.1284·v̄`，
即 `speed = c · sqrt(-2·ln(u))`，`u ~ uniform(0,1)`——**一行代码就能生成合理风速抖动**。
置信度：**高**（数学恒等式）。

> **诚实说明（本次调研已升级这段结论）**：
> **仍然成立**：**没有任何开源项目实现了「由纬度生成地表风」的生成器**
> （最接近的是 [sciforge-lib 的气象物理函数](https://docs.rs/sciforge-lib/0.0.4/src/sciforge_lib/meteorology/winds.rs.html)，
> 但那是给定气压梯度之后求解，不是气候态生成）；
> **也不存在任何闭式公式 `W(latitude)`** —— 标准做法是从 ERA5/NCEP 读纬向平均廓线。
>
> **本次补齐了什么**：
> 1. **风带的存在、方向、纬度边界现在是文献支撑的**（Stull Ch.11、Met Office、NOAA），置信度**高**；
> 2. **风速的绝对标定现在是实测的**（Lauscher 1951 全球 5.85 m/s；
>    Archer & Jacobson 2005 陆/海 10 m 分别为 3.28 / 6.64 m/s），置信度**高**；
> 3. §4.2 的陆地风速值由「实测纬向值 × 实测量测的陆海比 0.494」**导出**，置信度**中**。
>
> **仍然没有依据的部分（不要过分依赖）**：
> - 极地东风带的平均风速（**找不到任何实测**）；
> - ITCZ 位移对「某地主导风向」的影响量（幅度有实测，但把它加到固定方位角上是我们的构造）；
> - `seasonalFactor` 的 ±25%；
> - 副热带高压「静风」的具体速度下限。
>
> **结论**：§4 现在可以放心用于「让风向看起来合理（信风来自东北、西风来自西南）」
> 和「风速量级正确」，**但仍不能声称风向风速有预报技巧**。
> 真正的站点级风气候数据在 CLIGEN 的 `.PAR` 文件里（含 16 方位逐月统计，见 §8.3）。

## 5. 半球 / 时区处理

### 5.1 南北半球判定

```
hemisphere = (lat >= 0) ? Hemisphere.NORTH : Hemisphere.SOUTH
```

**注意：这是唯一正确的判据。** 本次调研发现 Minecraft 社群最大的系统性缺陷就在这里：

- **Serene Seasons（690 万下载）完全没有真实世界输入**——源码里没有纬度、经度、
  半球、时区、真实日期的任何痕迹。季节纯粹是游戏内 `dayTime` 的函数
  （一个游戏年 = 96 游戏日 ≈ 32 真实小时）。
- **Fabric Seasons 有** `isInNorthHemisphere` 布尔开关，但**只在「跟随系统时间」模式下生效**，
  且**没有经纬度**——只能用一个人工开关。
- **Weather Watch** 从 IP 地理定位推断半球；
- **Real Serene Seasons** 用「真实日历 + 半球开关 + 时区」；
- **所有固定偏移的时钟模组都忽略半球**。

也就是说：「按半球翻转季节相位」这件在气象学上**毫无争议**的事，
在 Minecraft 生态里**只有少数模组做对**。我们的 `hemisphere` 判据必须写对，
且应写成**从 `lat` 自动推导**而非人工开关。

### 5.2 由经度 + 时区估算当地太阳时

**只需经度与时区**，不需要天文库（置信度：**高**，公式来自
[NOAA Solar Calculator 计算细节](https://gml.noaa.gov/grad/solcalc/calcdetails.html)）。

#### 步骤 1：日角与太阳赤纬（Spencer 1971 级数）

```
γ = 2π * (dayOfYear - 1 + (utcHour - 12) / 24) / 365          // 弧度

δ = 0.006918
  - 0.399912*cos(γ)  + 0.070257*sin(γ)
  - 0.006758*cos(2γ) + 0.000907*sin(2γ)
  - 0.002697*cos(3γ) + 0.001480*sin(3γ)                       // 弧度
```

> **更简的替代（CLIGEN 源码里用的形式，误差 <0.5°）**：
> `δ = 0.4102 * sin( (dayOfYear − 80.25) / 58.13 )` 弧度。
> 来源：[CLIGEN `cligen.for`](https://infosys.ars.usda.gov/svn/code/third_party/climate/cli_gen/cligen.src/cligen.for)，置信度**高**。
> 若只需「大致日出日落时刻」，用这条就行。

#### 步骤 2：时差（Equation of Time）

```
EoT = 229.18 * ( 0.000075
               + 0.001868*cos(γ)  - 0.032077*sin(γ)
               - 0.014615*cos(2γ) - 0.040849*sin(2γ) )        // 分钟
```

> ⚠️ **系数陷阱**：NOAA 文档里写的是 `0.000075`，而
> [pvlib 的实现](https://github.com/pvlib/pvlib-python)（引用 Spencer 原始论文勘误）用的是 `0.0000075`。
> 两者差约 **1 秒**，无所谓，但**要固定用其中一个，别混**。
> 同一系列里 `0.040849` 常被印成 `0.04089`，用 `0.040849`。

#### 步骤 3：真太阳时与太阳位置

```
timeOffsetMin = EoT + 4 * lon - 60 * tzOffsetHours      // 东经为正、tz 为当地偏移
                                                          // （小时，含 DST）
trueSolarTimeMin = localClockHour * 60 + timeOffsetMin
hourAngleDeg     = trueSolarTimeMin / 4 - 180

cosZenith = sin(latRad)*sin(δ) + cos(latRad)*cos(δ)*cos(hourAngleRad)
```

**日出/日落的时角**（含 0.833° 大气折射，NOAA 标准做法）：

```
        ⎧ arccos( cos(90.833°)/(cos(lat)·cos(δ)) - tan(lat)·tan(δ) )   ← 一般情况
ωs  =   ⎨ 180°  若 arccos 参数 < −1     （极昼）
        ⎩ 0°    若 arccos 参数 > +1     （极夜）

白昼长度 N = (24/π) * ωs          小时
日出 = 太阳正午 − N/2 ;  日落 = 太阳正午 + N/2
太阳正午 ≈ 12:00 − EoT/60 − lon/15 + tzOffsetHours
```

**精度声明（NOAA 原话，置信度：高）**：
> 「日出日落结果在 **±72° 纬度以内理论精度在 1 分钟以内**，在此之外在 10 分钟以内。」
> 并且 NOAA 明确说明该计算器**已停止维护**。

**极昼/极夜分支必须实现**——否则 `acos` 的参数越界会返回 `NaN`，
在 |lat|>66.5° 时每年必然发生。这对 Minecraft 的雪原/冰刺群系是现实问题。

## 6. 引擎流程：把上面拼起来

```
输入：lat, lon, elevM, tzOffsetMin, dayOfYear, localHour, bio, lastObs(可空)

① 基础气候态（永远算，与是否有观测无关）
   T_clim     = §2.1 季节性基准 + §2.2 海拔订正
   DTR_clim   = §2.3.3 由 bio.humidity 与天气状态得到
   Tmax_clim  = T_clim + DTR_clim/2
   Tmin_clim  = T_clim - DTR_clim/2
   P_WW, P_WD = §3.2 马尔可夫链参数
   dirDeg     = §4.1 风带 + 季节位移
   speedKmh   = §4.2 风带基础 × 季节因子 × bioFactor

② 昼夜曲线
   sunrise, sunset, solarNoon = §5.2
   T_now_clim = §2.3.2 分段余弦(Tmin_clim, Tmax_clim, sunrise, sunset, localHour)

③ 若有 lastObs（无论多旧）——按 §3.3 实测的权重融合
   h_days = lastObsAgeHours / 24
   w      = 1 / (1 + (h_days / 2.10)^1.20)
   // 只对温度做融合，且用「距平」而非绝对值：
   T_anom_obs = lastObs.temperatureC - T_climAt(lastObs.time)
   T_now      = T_now_clim + w * T_anom_obs

   // 湿度：
   RH_now = w * lastObs.humidityPercent + (1-w) * (bio.humidity * 100)

   // 天气状态：观测越新，越倾向沿用观测的天气类型（持续性）
   pKeepObsWeather = w        // 见 §3.3：h=1 -> 0.71，h=3 -> 0.39
   if (rand() < pKeepObsWeather) weatherType = lastObs.weatherType
   else                          weatherType = §3.2 马尔可夫链采样

④ 无 lastObs（纯离线）——完全走气候态 + 马尔可夫链
   T_now = T_now_clim
   RH_now = bio.humidity * 100
   weatherType = §3.2 马尔可夫链采样（用「昨天」= 上一 tick 的状态）

⑤ 形态判定与群系校验（§3.1 + docs/BIOME_CLIMATE.md）
   if (weatherType 是降水类):
       形态 = §3.1 湿球/干球阈值判定
       if (形态 == SNOW && bio 白名单不含雪)     形态 = RAIN
       if (bio.precipitation == NONE)            weatherType = 最近的非降水类(CLOUDY/HAZE)
   T_now = clamp(T_now, bio.tempMinC, bio.tempMaxC)

⑥ 可信度（§8）
   confidence = f(lastObsAgeHours, bio.confidence, 数据完整度)
```

> **⚠️ 风速/风向的融合**：建议**不要**对风向做线性插值（角度插值需要处理 0/360 绕回），
> 简单地按 `w` 概率选择观测值或气候值即可。

## 7. 缓存设计建议

### 7.1 应缓存的字段

| 字段 | 必要性 | 说明 |
| --- | --- | --- |
| `observedAtEpochMs` | ✅ 必须 | **一切衰退逻辑的基准** |
| `temperatureC` | ✅ 必须 | 融合的主对象 |
| `humidityPercent` | ✅ 必须 | 湿球判定 + 日较差 + 融合 |
| `weatherType` | ✅ 必须 | 持续性沿用 |
| `windSpeedKmh` / `windDirection` | ✅ 建议 | 融合权重同上 |
| `pressureHpa` | 建议 | 气压趋势能指示天气变化（Δp/3h） |
| `cloudCoverPercent` | 建议 | 比 weatherType 更细，可用于日较差折减 |
| `dewPointC` | 建议 | 比 RH 更适合跨海拔换算 |
| `precipMmLastHour` | 可选 | 降水强度 |
| **`locationLat/Lon/ElevM`** | ✅ 必须 | 位置变了必须整条作废 |
| **`sourceProvider`** | ✅ 必须 | 换数据源时可信度不同 |
| **`apiReportedElevM`** | ✅ 必须 | **海拔订正**需要（见 §2.2 的坑） |
| `schemaVersion` | ✅ 必须 | 升级时丢弃旧缓存 |

### 7.2 多久算过期

**不要用「一刀切 TTL」**。过期是**连续衰退**，不是二值开关——
因为 §3.3 实测的 `w(h)` 曲线就是连续的。所以：

| 年龄 h | 最优权重 w | 语义 | 建议 |
| --- | --- | --- | --- |
| 0–1 h | 0.95–1.00 | 实况 | 直接用，不融合 |
| 1–3 h | 0.71–0.90 | 短期外推 | 融合，可信度「高」 |
| 3–12 h | 0.30–0.39 | 同期外推 | 融合，可信度「中」 |
| 12–48 h | 0.05–0.30 | 隔夜 | 融合，可信度「低」 |
| 2–7 d | 0.01–0.05 | 陈旧 | 只保留距平符号，可信度「很低」 |
| **> 7 d** | **≈ 0** | **等价于无数据** | **按纯离线处理；可保留缓存仅供 HUD 显示** |

**建议的 TTL 档位**：

```
HARD_TTL        = 7 天     // 超过则完全不参与融合（w < 0.02）
SOFT_TTL        = 24 小时  // 超过则 HUD 标注「数据陈旧」
REFRESH_INTERVAL= 取 API 的更新周期（Open-Meteo 15 min，UApiPro 视实况 ~15 min）
                        // 但不要更密——见下「不要过度轮询」
```

> **不要过度轮询**。调研中发现的真实事故：某模组默认 **10 秒**轮询 OpenWeatherMap，
> 即 **8,640 次/天**，而免费额度是 **1,000 次/天**；另一个每 5 秒构造一次
> SunriseSunset.io 请求（约 **17,000 次/天**）。
> 我们的 `minIntervalMillis()` 应当是 **15 分钟量级**，并配合指数退避。

### 7.3 缓存「跨季节 / 跨昼夜」过期怎么办

这是本设计的关键问题，有**两种不同的过期**，必须分开处理。

#### (a) 跨昼夜过期：**不要**用「昨天 14:00 的温度」当「今天 14:00」

温度有强烈的日循环（振幅 = DTR，本实测 5–14 K）。若缓存是昨天下午抓的、
现在是凌晨，直接沿用会**错一整个日较差（最多 ±7 K）**。

**正确处理**：缓存只提供**距平（anomaly）**，不提供绝对值。

```
// ✅ 正确：提取距平，再套到当前时刻的气候曲线上
T_clim_at_obs = 气候态温度(lastObs 时刻)         // 用 §2.1+§2.3 算
anomaly       = lastObs.temperatureC - T_clim_at_obs
T_now         = T_now_clim + w(h) * anomaly

// ❌ 错误：直接用绝对值
T_now = w * lastObs.temperatureC + (1-w) * T_now_clim
```

上面这句「错误」的写法，在 `T_clim_at_obs` 与 `T_now_clim` 相差 7 K 时
会引入同量级的系统性偏差。**这是最容易犯的错**。
（注：§3.3 实测里的 `anompers` 列就是这个正确做法，
它在 h=30 时 RMSE 4.23 K，而纯持续性 6.15 K —— 差距就来自这里。）

#### (b) 跨季节过期：**距平不能跨季沿用**

如果缓存是**冬天**抓的、现在是**夏天**，那么：
- 温度**距平**（如「比当月常年低 4 K」）**不能**直接搬到夏天——
  冬季的天气系统（寒潮、逆温）与夏季（对流、副高）机制不同。
- 所以**必须按年龄进一步削减**：上面 `w(h)` 曲线在 h=180 天时给出 w≈0.002，
  已经是实际上的 0，**这自然解决了跨季问题**。

```
// 显式加一道季节不连续保护
if (跨越了季节界限(lastObs.月, 当前月)) w *= 0.5      // 额外保守
if (|dayOfYear_now - dayOfYear_obs| > 90) w = 0        // 跨季超过一季 -> 弃用
```

**【工程近似】**（这两条阈值没有文献支撑，是基于 `w(h)` 曲线做的保守裁剪）。

#### (c) 湿度/天气类型跨昼夜

- **湿度**：日循环远弱于温度（通常 ±10–20%），可以直接按 `w` 融合，**不需要**距平处理。
- **天气类型**：`pKeepObsWeather = w` 已经处理了。「昨天下午在下雨」到「今天凌晨」
  时 w≈0.6，有 40% 概率切换到气候态采样——合理（雨通常持续数小时到一天，不是数天）。
- **风**：按 `w` 概率选择，不做插值。

### 7.4 缓存要持久化到磁盘

离线场景的前提就是「进程可能重启」。所以缓存**必须**写盘
（`config/NowWeather/cache/last_observation.json` 或世界存档 `SavedData`），
否则「上次成功获取的观测与时间戳」这个输入在重启后就丢了，
纯离线分支永远拿不到 `lastObs`。

> 注意：调研发现 [Serene Seasons 的官方 FAQ](https://github.com/Glitchfiend/SereneSeasons/wiki)
> 明确记载了「睡眠/改时间导致 tick 跳过」「不重启切换存档导致季节时间脱同步」这类 bug，
> 并有第三方修复模组专门处理。**我们自己的缓存也要注意同一类问题**：
> 用**真实世界 epoch 时间戳**，不要用游戏内 tick 计数。

**通用的缺陷分类（对我们的设计有直接指导意义）**：

1. **时标错配是根本问题，没人解决**。MC 是真实时间的 **72 倍**；一个真实年压缩进去要 26,297 游戏日。
   所以「真实季节」模组必须二选一：(a) 跟随真实日历 → 季节每 3 个真实月才变一次，
   正常游戏时段内**根本看不到季节变化**；(b) 保留加速年（Serene Seasons ≈ 32 真实小时/年）→ 与现实脱钩。
   **本调研中的每个设计都选了其中一头，没有一个做插值。**
   → **我们的设计必须明确选 (a)**，因为需求是「离线推算真实天气」而非「加速季节循环」。
2. **DST 是系统性 bug**。任何整数 UTC/GMT 偏移**都无法**表达 DST。
   只有 tz 数据库名（`Europe/Berlin`）或 `LocalDateTime.now()` 才对。
   → 我们的输入用 **`tzOffsetMin`（含 DST 后的实际偏移，分钟）**，不是整数小时，天然正确。
3. **半球处理罕见且不一致**。显式支持：Weather Watch、Real Serene Seasons、Fabric Seasons（仅系统时间模式）。
   **基础版 Serene Seasons、Weather2、PMA、Project Atmosphere、所有 OWM 城市插件都缺失。**
4. **HUD/视觉可信度与真实不一致**。「逐玩家发包」和「改世界状态」是两条互斥路线，没人两头都做对。
5. **配额与轮询事故**。见 §7.2。
6. **原版降水 bug 会被季节模组放大**：[MC-259935](https://mojira.dev/MC-259935)
   「群系降水设为 NONE 时仍会下雪」——25w31a 之前 `Biome#doesNotSnow()` **只查温度、不查降水标志**。
   季节模组通过把温度压到 0.15 以下造雪，正好复现这个失效模式。
   → 我们已经在 §3.1 ⑤ 用应用层白名单挡住了。

#### CLIGEN 的完整可借用公式（源码逐行核实，置信度：**高**）

CLIGEN 是本次调研中**唯一**一个把所有生成方程都写在可读源码里的天气发生器，
且**只依赖 12 个月度统计量**——非常适合我们这个「无大数据集」的场景。

**① 降水发生 —— 一阶两状态马尔可夫链**（已在 §3.2 采用）

```fortran
prw(1,mo) = P(W|D) ;  prw(2,mo) = P(W|W)
vv = randn(k1)
if ((prw(l,mo).le.0.0).or.(vv.gt.prw(l,mo))) then r=0; l=2; else ...; l=1
```

**② 降水量 —— Pearson III 型分布**（由月均值 μ、标准差 s、偏度 g）

```
R = R̄ + (2s/g)·{ [ (g/6)·(x − g/6) + 1 ]³ − 1 },     x ~ N(0,1)
```

v5.200 把月度降水偏度裁剪到 ±4.5（因为 Pearson III 会产生负值）。
标准正态用 Box–Muller：`sqrt(-2·ln(u1))·cos(2π·u2)`。置信度：**高**。

**③ Tmax/Tmin —— v5 的「耦合」方案（比 v4 好，且只有它能避免一个已知偏差）**

v4.2 用两个**独立**正态分布，然后强制 `if (Tmin > Tmax) Tmin = Tmax − 0.2·|Tmax|`。
源码注释承认这**「改变了 Tmin 的分布，使输出均值低于生成它的输入均值」**——真实偏差。

v5 改成耦合（源码注释 V-5.224 / V-5.2253）：**先生成标准差较小的那一个**，另一个由**日较差 ΔT** 生成。

```
if (σ_Tmin <= σ_Tmax):
    Tmin = μ_Tmin + z·σ_Tmin
    σ_Δ  = sqrt(σ_Tmax² − σ_Tmin²)
    Δμ   = μ_Tmax − μ_Tmin
    Tmax = Tmin + Δμ + z·σ_Δ
else:
    Tmax = μ_Tmax + z·σ_Tmax
    σ_Δ  = sqrt(σ_Tmin² − σ_Tmax²)
    Tmin = Tmax − Δμ − z·σ_Δ          // 注意符号翻转
```

露点同理，用 `σ² = |((σ_Tmax+σ_Tmin)/2)² − σ_other²|`。
**这套方案只需要 12 个月的 μ 和 σ，就能生成统计上正确的 Tmax/Tmin 对**——
比我们自己的「正弦 + 日较差」方案在**统计分布**上更严谨，
值得作为「有月度气候数据时」的升级路径。置信度：**高**。

**④ 风速/风向 —— 16 方位 Pearson III（不是 Weibull）**

参数文件里每个月、每个方位 j = 1…16 带四个数：
`%时间`（累积成 `dir(m,j)`）、`均值`、`标准差`、`偏度`；另有 `calm(m)` = 静风比例。

```
方向：u ~ U(0,1)；找第一个 dir(m,j) > u 的 j
      g = (u − dir(m,j−1)) / (dir(m,j) − dir(m,j−1))
      θ = 2π·(g + j − 1 − 0.5)/16        // 从北起算的弧度
      （若无匹配 -> 静风日：速度 0，方向 0）
速度：Pearson III，与降水量同一形式，g = 该方位偏度（为 0 时强制为 0.01）
      if (wv < 0) wv = 0.1 m/s
跨月插值：运行期选项 -I1 线性、-I2 傅里叶、-I3 保均值
```

**⑤ 逐日太阳辐射**

```
δ = 0.4102·sin((J − 80.25)/58.13)                     // 弧度
h = acos(−tan(lat)·tan(δ)/1)  , 裁剪到 [0, π]
rmx = 711.0·(h·sin(lat)·sin(δ) + cos(lat)·cos(δ)·sin(h))   // langleys/day，理论最大值
ra  = obsl(mo) + z·stdsl(mo)                           // v5.322，裁剪到 [0.05·rmx, rmx]
```

**⑥ 源码里明确写下的警告（值得抄进我们自己的文档）**

`Readme.2nd` 原文：
> *「日最高温、最低温、降水量和辐射是作为**独立分布**生成的……除最低温在 v5 中已耦合外，
> 最高温、最低温、太阳辐射、降水量都作为独立分布生成。有人指出这些参数在物理世界上并不独立。」*

也就是说，**即便是业界最强的统计发生器，也承认这些量之间的物理耦合没有被建模**。
这正好说明为什么我们的「先算温度 → 再算相态 → 再算降水」的**因果链**是合理的补强，
同时也提醒我们：**不要声称统计上已经自洽**。

## 9. 完整伪代码

> 目标：**能直接照着写 Java**。类型已标注，`// 文献` / `// 工程` 标明来源性质。

```java
// ============================================================================
// OfflineWeatherSynthesizer —— 输入元数据 + 可选上次观测 -> 合成天气
// ============================================================================

/** 输入：地点元数据（必填） */
record PlaceMeta(
    double  latDeg,          // 北正南负
    double  lonDeg,          // 东正西负
    double  elevM,           // 海拔（米）
    int     tzOffsetMinutes, // 含 DST 后的实际偏移（分钟）
    int     dayOfYear,       // 1..366
    double  localHour        // 0.0..24.0，玩家本地时钟
) {}

/** 输入：生物群系气候（来自 docs/BIOME_CLIMATE.md 的 BiomeClimate） */
record BiomeClimate(
    double tempMinC, double tempMaxC,       // 正常温度范围
    double humidity01,                      // 0..1
    double windiness01,                     // 0..1
    boolean precipitationAllowed,           // precipitation != NONE
    boolean snowAllowed,                    // 白名单含雪
    ClimateClass climateClass,
    Confidence confidence
) {}

/** 输入：上次成功观测（可空） */
record LastObservation(
    long   observedAtEpochMs,
    double temperatureC,
    double humidityPercent,
    double windSpeedKmh,
    double windDirectionDeg,   // 来向
    String weatherType,
    double dayOfYearAtObs,
    long   ageHours            // 由 now - observedAtEpochMs 算出
) {}

/** 输出 */
record SynthesizedWeather(
    double  temperatureC,
    String  weatherType,        // CLEAR/PARTLY_CLOUDY/CLOUDY/OVERCAST/RAIN/SNOW/SLEET/...
    double  humidityPercent,
    double  windSpeedKmh,
    double  windDirectionDeg,
    double  confidence01,       // 0..1
    String  reason              // 供 HUD / 日志："offline-climatology", "blended(w=0.71)"
) {}

// ============================================================================
public final class OfflineWeatherSynthesizer {

    // ---- 常量（全部标注来源） ----
    private static final double YEAR_DAYS      = 365.25;
    private static final double PEAK_DAY_NORTH = 202.0;   // 实测均值 202.2，[实测]
    private static final double PEAK_SHIFT_S   = 182.6;   // = 365.25/2，[实测验证]
    private static final double LAPSE_K_PER_KM = 6.5;     // ISA 标准，[文献·高]
    private static final double RAIN_SNOW_T_C  = 1.2;     // Dai 2008 陆地值，[文献·高]
    private static final double PHASE_HALFWIDTH= 2.5;     // -> 过渡带 -1.3..+3.7，[工程]
    private static final double WETBULB_T_C    = 0.5;     // Steinacker 1983，[文献·中高]
    private static final double BLEND_H0       = 2.10;    // 实测最优 w 拟合，[实测]
    private static final double BLEND_Q        = 1.20;    // 实测最优 w 拟合，[实测]

    // ========================================================================
    public SynthesizedWeather synthesize(PlaceMeta p, BiomeClimate bio,
                                         LastObservation obs /* 可空 */) {

        final boolean south = p.latDeg() < 0.0;              // §5.1 唯一正确判据
        final double  absLat = Math.abs(p.latDeg());
        final double  peakDay = PEAK_DAY_NORTH + (south ? PEAK_SHIFT_S : 0.0);

        // ---------- ① 太阳几何（§5.2） ----------
        final Solar solar = Solar.of(p);      // sunrise/sunset/solarNoon/declination

        // ---------- ② 季节性基准温度（§2.1, §2.2） ----------
        // 2a. 海平面年振幅：优先用 climateClass 查表，否则用纬度回归兜底
        final double continentality = 1.0 - bio.humidity01();           // [工程·低]
        final double amp = amplitudeK(absLat, continentality);           // §2.1.1

        // 2b. 海拔订正（在算 annual mean 时施加）
        final double annualMeanSeaLevel = annualMeanSeaLevelC(absLat);   // §2.1.1 / 表
        final double annualMean = annualMeanSeaLevel
                                - LAPSE_K_PER_KM * (p.elevM() / 1000.0); // [文献·高]

        // 2c. 季节性基准
        final double seasonC = annualMean
            + amp * Math.cos(2.0 * Math.PI * (p.dayOfYear() - peakDay) / YEAR_DAYS);

        // ---------- ③ 天气状态：马尔可夫链（§3.2） ----------
        // 注：真正的实现应把「昨天是否湿」持久化；纯离线首帧用稳态概率采样
        final MarkovParams mk = MarkovParams.fromBiome(bio);            // P_WW, P_WD
        final boolean isWetDay = previousDayWasWet
            ? rng.nextDouble() < mk.pWW()
            : rng.nextDouble() < mk.pWD();

        // ---------- ④ 日较差与昼夜曲线（§2.3） ----------
        // 4a. 由湿度得晴天日较差（实测 R^2 = 0.797）
        final double dtrClear = clamp(18.10 - 0.1398 * (bio.humidity01() * 100.0),
                                      4.0, 16.0);                        // [实测/工程]
        final double cloudFactor = cloudFactorFor(bio, isWetDay);        // §2.3.3
        final double dtr = dtrClear * cloudFactor;

        double tMaxClim = seasonC + dtr / 2.0;
        double tMinClim = seasonC - dtr / 2.0;

        // 4b. 分段余弦日变化（Tmin 在日出、Tmax 在正午后 2.5 h）
        double tNowClim = diurnalCurve(tMinClim, tMaxClim, solar, p.localHour());

        // ---------- ⑤ 与上次观测融合（§3.3 实测权重） ----------
        double w = 0.0;
        double rh;
        String weatherType;
        String reason;

        if (obs != null) {
            final double hDays = obs.ageHours() / 24.0;
            // 实测最优权重：w = 1 / (1 + (h/2.10)^1.20)   [实测]
            w = 1.0 / (1.0 + Math.pow(hDays / BLEND_H0, BLEND_Q));

            // 跨季保护（§7.3b）[工程]
            final double seasonGap = Math.abs(wrap(p.dayOfYear() - obs.dayOfYearAtObs(), 365.25));
            if (seasonGap > 90.0) w = 0.0;
            else if (seasonGap > 45.0) w *= 0.5;

            // ★ 关键：融合「距平」而不是「绝对值」（§7.3a）
            final double tClimAtObs = climatologyAt(obs.dayOfYearAtObs(), solar, /*...*/);
            final double anomaly    = obs.temperatureC() - tClimAtObs;
            tNowClim = tNowClim + w * anomaly;

            // 湿度：日循环弱，可直接融合
            rh = w * obs.humidityPercent() + (1.0 - w) * (bio.humidity01() * 100.0);

            // 天气类型：按 w 的概率沿用观测（持续性）
            weatherType = (rng.nextDouble() < w)
                        ? obs.weatherType()
                        : sampleMarkovWeather(mk, isWetDay);
            reason = String.format("blended(w=%.2f, age=%.1fh)", w, obs.ageHours());
        } else {
            rh = bio.humidity01() * 100.0;
            weatherType = sampleMarkovWeather(mk, isWetDay);
            reason = "offline-climatology";
        }

        // ---------- ⑥ 相态判定（§3.1） ----------
        if (precipitates(weatherType)) {
            final double tw = wetBulbC(tNowClim, rh);                   // Stull 2011 [文献]
            final double thr = (rh > 5.0) ? WETBULB_T_C : RAIN_SNOW_T_C;
            final double tv  = (rh > 5.0) ? tw : tNowClim;

            if (tv >= thr + PHASE_HALFWIDTH)      weatherType = "RAIN";
            else if (tv <= thr - PHASE_HALFWIDTH) weatherType = "SNOW";
            else                                  weatherType = "SLEET";

            // 群系白名单校验（§3.1 ⑤，对应 MC-259935 的教训）
            if (!bio.precipitationAllowed())            weatherType = "OVERCAST";
            else if (weatherType.equals("SNOW") && !bio.snowAllowed()) weatherType = "RAIN";
        }

        // ---------- ⑦ 温度范围夹取（docs/BIOME_CLIMATE.md） ----------
        double tempC = clamp(tNowClim, bio.tempMinC(), bio.tempMaxC());

        // ---------- ⑧ 风（§4） ----------
        final double windDir = windDirectionDeg(p.latDeg(), p.dayOfYear(), peakDay);
        final double baseWind = baseWindKmh(absLat);
        final double seasonal = 1.0 + 0.25 * (-Math.cos(
                2.0 * Math.PI * (p.dayOfYear() - peakDay) / YEAR_DAYS));
        final double windKmh = baseWind * seasonal * (0.6 + 0.8 * bio.windiness01());
        // 加 Weibull(k=2) 抖动：c = v̄/0.8862，speed = c*sqrt(-2 ln u)
        final double jitter = Math.sqrt(-2.0 * Math.log(Math.max(1e-9, rng.nextDouble())));
        final double windFinal = windKmh * jitter / 1.2533;  // 除以 E[Rayleigh] 保持均值

        // ---------- ⑨ 可信度（§10） ----------
        final double conf = confidence(bio.confidence(), obs, w, bio);

        return new SynthesizedWeather(tempC, weatherType, rh, windFinal, windDir, conf, reason);
    }

    // ==================================================================== //
    //  辅助函数 —— 每个都给出对应的公式来源
    // ==================================================================== //

    /** §2.1.1 振幅查表 + 海陆插值 */
    private static double amplitudeK(double absLat, double continentality) {
        double maritime, continental;
        if      (absLat < 10) { maritime = 1;  continental = 3;  }
        else if (absLat < 20) { maritime = 2;  continental = 6;  }
        else if (absLat < 30) { maritime = 4;  continental = 10; }
        else if (absLat < 45) { maritime = 7;  continental = 13; }
        else if (absLat < 60) { maritime = 9;  continental = 16; }
        else                  { maritime = 11; continental = 22; }
        return maritime + (continental - maritime) * clamp01(continentality);
    }

    /** §2.3.2 分段余弦日变化 */
    private static double diurnalCurve(double tMin, double tMax,
                                       Solar s, double hour) {
        double tMinH = s.sunriseHour();
        double tMaxH = s.solarNoonHour() + 2.5;      // 正午后 2.5 h
        if (tMaxH <= tMinH) tMaxH = tMinH + 9.0;     // 极夜兜底

        if (hour >= tMinH && hour < tMaxH) {
            double ph = (hour - tMinH) / (tMaxH - tMinH);
            return tMin + (tMax - tMin) * 0.5 * (1.0 - Math.cos(Math.PI * ph));
        } else {
            double span = (24.0 - tMaxH) + tMinH;
            if (span <= 0) span = 15.0;
            double ph = mod24(hour - tMaxH) / span;
            return tMin + (tMax - tMin) * 0.5 * (1.0 + Math.cos(Math.PI * ph));
        }
    }

    /** §3.1 Stull (2011) 湿球温度，无迭代 */
    private static double wetBulbC(double tC, double rhPercent) {
        double rh = clamp(rhPercent, 5.0, 99.0);     // 公式有效范围
        return tC * Math.atan(0.151977 * Math.sqrt(rh + 8.313659))
             + Math.atan(tC + rh)
             - Math.atan(rh - 1.676331)
             + 0.00391838 * Math.pow(rh, 1.5) * Math.atan(0.023101 * rh)
             - 4.686035;
    }

    /** §4.1 风带 + 季节位移（全部为工程近似） */
    private static double windDirectionDeg(double lat, int doy, double peakDay) {
        double a = Math.abs(lat);
        double base;
        if      (a < 5)  return Double.NaN;                       // 赤道辐合带：无主导风向
        else if (a < 30) base = (lat > 0) ? 45 : 135;             // 信风 NE / SE
        else if (a < 60) base = (lat > 0) ? 225 : 315;            // 西风 SW / NW
        else             base = (lat > 0) ? 45 : 135;             // 极地东风 NE / SE
        double shift = 10.0 * Math.sin(2*Math.PI*(doy - peakDay)/YEAR_DAYS);
        return mod360(base + shift);
    }

    /** §4.2 风带基础风速（工程近似） */
    private static double baseWindKmh(double absLat) {
        if (absLat < 5)  return 6;    // 赤道辐合带
        if (absLat < 25) return 14;   // 信风带
        if (absLat < 32) return 8;    // 副热带高压（弱风带）
        if (absLat < 60) return 18;   // 西风带（最强）
        return 15;                    // 极地东风带
    }

    /** §3.2 无月气候数据时由生物群系近似马尔可夫参数（工程近似） */
    private static MarkovParams MarkovParams_fromBiome(double hum01) {
        double pww = clamp(0.15 + 0.73 * hum01, 0.10, 0.90);
        double wetFrac = clamp(1.15 * hum01 - 0.30, 0.01, 0.95);
        // 用稳态关系反解 P_WD：  P(W) = P_WD / (1 - P_WW + P_WD)
        double pwd = wetFrac * (1.0 - pww) / Math.max(1e-6, 1.0 - wetFrac);
        return new MarkovParams(pww, clamp(pwd, 0.005, 0.70));
    }

    /** §10 可信度 */
    private static double confidence(Confidence bioConf, LastObservation obs,
                                     double w, BiomeClimate bio) {
        double base = switch (bioConf) {
            case HIGH   -> 0.80;
            case MEDIUM -> 0.65;
            case LOW    -> 0.45;
            case GUESS  -> 0.30;
        };
        // 有观测则按权重提升（w 已在 [0,1]）
        double withObs = base + (0.95 - base) * w;
        // 无降水白名单 / 无湿度字段 -> 打折
        if (!bio.precipitationAllowed()) withObs *= 0.95;
        return clamp01(withObs);
    }
}
```

## 10. 误差评估（**不夸大**）

### 10.1 温度

| 场景 | RMSE | 依据 |
| --- | --- | --- |
| **纯离线（无任何观测）**，逐日 Tmax/Tmin | **3.2 – 3.4 K**（本实测 14 站均值） | 气候态 RMSE，实测 |
| **纯离线**，赤道站（Singapore） | **0.74 K** | 实测 |
| **纯离线**，温带海洋性（London） | **2.8 K** | 实测 |
| **纯离线**，极端大陆性（Yakutsk） | **5.1 K** | 实测 |
| **纯离线**，瞬时时点（含昼夜曲线误差） | **+1 – 3 K 附加** | 由日较差 5–14 K 与 Tmin/Tmax 时点误差推断【工程估计】 |
| **缓存 1 天 + 融合** | **2.3 – 2.9 K**（比纯离线改善 7–31%） | 实测最优混合 |
| **缓存 2 天 + 融合** | **2.9 K**（与纯离线打平） | 实测 |
| **缓存 ≥3 天** | **≈ 纯离线水平，融合不再有增益** | 实测 |

**→ 结论：离线温度误差约 ±3 K（1σ），即约 2σ ≈ ±6 K 的 95% 区间。**

需求里问的「±3~5 °C」：**在温带/亚热带是合理的（3–4 K）**；
**在赤道偏乐观**（可以做到 <1 K）；
**在极端大陆性气候偏乐观**（Yakutsk 5.1 K，且我们的振幅查表法
在无海陆数据时还会再差 ±5 K，因为振幅 R² 只有 0.60）。

> ⚠️ **最大的单项误差来源不是模型，而是「振幅未知」**。
> 如果只按纬度取振幅，Miami 与 Riyadh 同纬度但振幅差 3 倍，你无法区分 —— 单项误差可达 ±5 K。
>
> ✅ **这一项已于第二轮调研中实测解决**（§2.4 方案 D）：
> `A = sin(|lat|)·(9.1 + 18.1·d/(d+400))`，`d` = 距海岸距离，
> **留一交叉验证 RMSE 2.5 K**（只用纬度是 4.45 K，**降低约 40%**），
> 成本是一张 **约 2 kB** 的陆海位图（2° 分辨率即可，退化 < 1.7 K）。
> **因此 §10.1 表格里「纯离线 3.2–3.4 K」这个数字应当随此改进而下降** ——
> 但那个 3.2 K 是在「只有纬度」的前提下测的，**接入方案 D 后需要重新实测**，
> 目前**不要**直接把 3.2 K 改小。保守预期：中纬度可改善到约 **2.5–3.0 K**。
>
> ⚠️ **方案 D 的已知失效区**（别指望它全域有效）：
> 东西伯利亚/加拿大内陆的极端大陆性（Yakutsk 实测误差 **+10 K**）、
> 东岸沿海（Tokyo +5.6、Halifax +4.5）、低纬高原（Brasilia −4.5）。
> 这些区域仍需 `ClimateResolver` 覆盖接口。

#### 10.1.1 这个精度放在「气象学坐标系」里是什么水平

孤立地看「±3 K」没有意义。**必须和两个参照物比**：

| 参照物 | 逐日温度 RMSE | 来源 |
| --- | --- | --- |
| **业务数值预报 第 1 天** | **≈ 1.2 – 1.3 K** | 由「次日最高温误差 ≤2 °C 的概率 90%（BOM）/ 93%（Met Office）」反推（高斯假设，σ ≈ 2/1.645） |
| **业务数值预报 第 5 天** | **≈ 1.8 K** | 由「第 5 天 73%（最高温）/ 70%（最低温）在 ±2 °C 内」反推 |
| **持续性（persistence）基准** | **≈ 2.6 K**（ACC ≈ 0.67，欧洲格点、24 h 滞后） | *Geosci. Model Dev.* **15**:8931–8956 (2022), [doi:10.5194/gmd-15-8931-2022](https://doi.org/10.5194/gmd-15-8931-2022) |
| **本离线模型（纯离线）** | **3.2 – 3.4 K** | 本项目实测 |
| **本离线模型（缓存 1 天）** | **2.3 K** | 本项目实测 |

**这张表说明三件事**：

1. **本项目的实测与独立文献吻合得很好**：我测得 h=1 持续性 RMSE = **2.49 K**，
   而文献上欧洲格点的持续性基准是 **≈2.6 K** —— 两者独立、量级一致，
   这反过来增强了本报告整套实测方法的可信度。（置信度：**高** —— 两个独立来源互证）
2. **离线模型在「缓存 1 天」时（2.3 K）已经优于持续性基准（2.6 K）**，
   但仍比业务第 1 天预报差约 **2 倍**。
3. **纯离线（3.2 K）在任何意义上都不是预报** —— 它和「持续性」这种
   毫无技巧的方法打平甚至更差。这正是 §3.3 那张衰减表要传达的信息。

### 10.2 天气类型

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| 「晴天」类别准确率 | **65% – 98%** | 实测（14 站） |
| **但其中大部分来自基础概率**：Cairo 湿日只占 2.2%，「永远说晴」就有 97.8% | — | **这是最容易用来吹牛的数字** |
| **马尔可夫链 vs 气候态的 Brier 技巧分** | **+0.090**（合计） | **实测。这才是真实技巧** |
| 极干旱气候（Cairo） | **−0.016**（比气候态略差） | 实测 |
| 最佳站（Windhoek） | +0.191 | 实测 |
| 降水**持续性**基线命中率 | 60.8% – 96.3%（均 ~75%） | 实测，同样受基础概率支配 |

**→ 结论：**
- **不要声称「天气类型命中率 X%」而不加限定。** 唯一诚实的说法是：
  **「在干旱气候下准确率天然很高（因为不下雨），但马尔可夫链相对气候态的净技巧只有约 +0.09 Brier」。**
- 判定**雨/雪形态**则可靠得多：过渡带只有 ±2.5 K 宽，
  而我们的温度 RMSE 是 3.2 K，所以**在 0 °C 附近 1–2 K 的区间内会有约 20–40% 的形态判错**；
  在明确远离阈值的温度上，形态判定近乎无误。
- **业务级对照**：ECMWF/GFS 在**第 1 天**的降水预报本身也只有中等技巧；
  我们的目标不是达到它，而是「在没有数据时保持合理与连贯」。

### 10.3 风

| 指标 | 数值 | 依据 |
| --- | --- | --- |
| 风向 | **只有按纬度带的大致方向**，误差按 45°–90° 量级 | 工程近似，**无实测验证** |
| 风速 | **量级正确（±50% 以内）**，不可当作预报 | 工程近似 |

**⚠️ 风是本文档中置信度最低的部分。**
定性结论（信风/西风/极地东风带的存在与方向）是教科书事实，
但本文档给的具体角度与速度值**全部是为可实现而构造的占位值**。
若需要真实风气候，必须接入 §8.3 的 CLIGEN `.PAR` 数据。

### 10.4 可信度（confidence）字段的建议映射

```
confidence = base(bio.confidence)
           + (0.95 - base) * w(h)              // 有观测则按实测权重提升
           * (跨季保护系数)                     // §7.3b
           * (数据完整度打折)                   // 缺湿度 / 缺海陆 / 缺月气候态
```

建议的实际区间：

| 状态 | confidence |
| --- | --- |
| 缓存 <1 h | 0.90 – 0.95 |
| 缓存 1–3 h | 0.75 – 0.90 |
| 缓存 3–24 h | 0.55 – 0.75 |
| 缓存 1–3 d | 0.40 – 0.55 |
| 缓存 3–7 d | 0.30 – 0.40 |
| **纯离线**（从未拿到数据） | **0.30 – 0.50**（取决于 `BioClimate.confidence`） |
| 纯离线 + 群系是 `GUESS` | 0.30 |

> ⚠️ **纯离线的可信度不应该高于 0.5。** 因为实测的净技巧（Brier +0.09）
> 和温度 RMSE（3.2 K）都说明它只是「合理的默认值」，不是预报。
> 建议 HUD 在纯离线时明确显示「离线推算」而不是把数字当作实况展示。

## 11. 总结（≤500 字）

**最关键的 3 个公式**

1. **季节温度**：`T = [T̄(lat) − 6.5·elev/1000] + A(lat,海陆)·cos(2π(doy−peak)/365.25)`，
   `peak = 202 + (南半球?182.6:0)`。202（非夏至 171.5）与 +182.6 均由 14 站 ERA5 实测验证。
   `A` 必须含海陆性——只靠纬度 R² 仅 0.60（Miami 25.8°N 振幅 3.5K，Riyadh 24.7°N 11.3K）。

2. **缓存衰退权重**：`w(h)=1/(1+(h/2.10)^1.20)`，h 为距上次观测天数（实测最优拟合，SSE=0.002）。
   h=1→0.71，3→0.39，7→0.19，30→0.04。必须**融合距平**：`T=T_clim(now)+w·(T_obs−T_clim(obs))`；
   用绝对值会引入最多 7K 偏差。

3. **雨雪相态**：用**湿球**判据，50% 点在 `Tw=0.5°C`，过渡带 ±2K（Steinacker 1983）；
   湿球用 Stull(2011) 闭式近似。干球回退阈值 `1.2°C`（Dai 2008），过渡带 (−1,+3)°C（USACE 1956）。
   **阈值不是 0°C**。

**精度上限**

- **温度 ±3K（1σ）**：这是气候态 RMSE 的硬下限，14 站实测均值 3.2–3.4K，任何离线方法都不会显著更优。
  赤道 <1K，极端大陆性可达 5K。
- **天气类型净技巧极低**：类别准确率 65–98% 主要来自基础概率（沙漠「永远说晴」即 98%）；
  相对气候态的 Brier 技巧分**仅 +0.09**，极干旱气候甚至为负。
- **风只有量级与大致方向**，不可用。
- **离线 >3 天融合无增益；>7 天缓存作废。**

**一句话**：能让无数据时的天气**合理、连贯、季节正确**，温度接近真实，
但**不能预测天气变化**——不应在 UI 上呈现为预报。

> ⚠️ **对中文用户的实际影响**：东亚季风东岸正是本模组的主力用户所在地
> （杭州/上海/东京这一带）。方案 D 在这些地方会**低估**季节振幅，
> 而原来的「只按纬度」公式因为系数偏大，反而更接近季风气候的实际值。
> 这是一个**用全球平均精度换局部精度**的取舍，已如实记录，没有掩盖。
> 正确的修法不是继续调这条公式，而是让这些群系在气候数据里显式覆盖
> `seasonalAmplitude`（`ClimateModifier` 扩展点已经支持）。
