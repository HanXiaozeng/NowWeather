## 0. 为什么必须用真机服务端测

第一轮尝试用 ForgeGradle 的 `runServer`（开发环境），结果 **TerraBlender 直接崩在启动阶段**：

```
Mixin apply failed terrablender.mixins.json:MixinNoiseGeneratorSettings
  -> @Shadow field f_188871_ was not located in the target class NoiseGeneratorSettings
```

原因：开发工作区用的是 **Mojang 官方映射**，而 BOP/TerraBlender 这类带 mixin 的生产模组是按 **SRG 名字**编译的 ——
它们的 refmap 在开发环境里对不上。**这是开发环境的固有限制，不是模组兼容性问题。**

换成真实的 Forge 服务端（`forge-1.18.2-40.3.12-installer.jar --installServer`）后，BOP 与 TerraBlender 全部正常加载。
顺带还验证了 **reobf 之后的生产 jar** 是可用的（这比开发环境更接近玩家实际环境）。

## 5. 测试中发现并修掉的两个真 bug

真机测试的价值就在这里 —— 这两个问题在离线单测里都测不出来：

### 5.1 没有玩家时主循环每 5 刻抛一次异常

```
java.lang.IllegalArgumentException: ForecastRequest 需要生物群系气候
  at ForecastRequest.<init> ─ ForecastRequest$Builder.build ─ buildOfflineObservation ─ tick
```

服务器上暂时没有玩家 → 取不到生物群系 → `climate == null` → 离线兜底仍然去构造预报请求 → 抛异常。
（异常被主循环的防御性捕获挡住，**没有崩服**，但日志被刷屏、离线兜底实际失效。）

**修复**：没有群系上下文时返回中性观测，不做气候校验；同时给主循环异常加上「同类错误每分钟最多报一次」的节流。

### 5.2 读天气状态读错了 API

```java
// Level#isRaining() 的字节码：
//   getRainLevel(1.0F) > 0.2   ← 读的是「插值后的渲染等级」，不是真实天气标志
```

后果：刚设置完天气时，`isRaining()` 要过十几刻才越过 0.2 的阈值；
控制器会误判「天气没变」，于是每个冷却周期都重设一次天气 —— 而**不断重设正是原版天气计时器被反复重置的原因**
（这也是社区里天气类模组最常被抱怨的问题）。

**修复**：改读原始标志 `level.getLevelData().isRaining() / isThundering()`。
修复前后自检的「回读不一致」次数：**577 → 0**。

### 5.3 顺带加上的「不跟服主对着干」保护

- `doWeatherCycle=false`（服主冻结天气）时，模组只提供数据、不修改天气；
- 检测到其它天气模组控制天气时进入观察模式（配置项 `yieldToOtherWeatherMods`，默认开）。

### 9.2 ★ mods.toml 里的可选依赖版本范围会「炸掉整个模组」

我给 1.18.1 的 `mods.toml` 写了：

```toml
[[dependencies.nowweather]]
modId = "biomesoplenty"
mandatory = false
versionRange = "[14,)"
```

而 BOP 1.18.1 的版本号是 **`1.18.1-15.0.0.105`** —— Forge 按 Maven 版本规则比较时，

```

Currently, "biomesoplenty" is "1.18.1-15.0.0.105"
```

**处理**：删掉这个可选依赖声明。本模组对群系模组的支持是**数据驱动**的
（内置气候表 + 按 id/标签/关键词/基础温度推断），既不依赖对方的 API，也不需要声明依赖 ——
声明它反而引入风险。（1.18.2 侥幸没炸，是因为 BOP 1.18.2 的版本号是不带 MC 前缀的 `16.0.0.134`。）

### 9.3 自检命令没考虑「按配置保持原版」的新分支

## 10. 下界 / 末地 / 虚空：完全保持原版（本轮新增的硬保证）

需求原话：「在末地和下界的群系全部保持原版，不要动哦」。

实现方式不是「少动」，而是**根本不下场**：

```java
// SyncPolicy.decide：下界/末地/虚空直接返回「不改动」，durationTicks = 0
if (config.leaveNetherAndEndAlone() && climate != null && climate.climateClass().isWeatherFree()) {
    return new WeatherDecision(current, 0, 0, temperature, type, false,
            "下界/末地/虚空保持原版天气（leaveNetherAndEndAlone=true）", tick, List.of());
}
```

控制器里 `durationTicks <= 0` 的决策会直接 return，**连 `setWeatherParameters` 都不会被调用** ——
原版的天气计时器、`doWeatherCycle`、`/weather clear` 状态完全不受影响。

离线验证（`IntegrationTests.netherAndEndUntouched`）：

- 假装当前正在下雨 → 灌入 40°C 的雷阵雨 → 下界群系：**写入次数 0、天气仍是雨、决策持续时间 0**；
- 同一份观测灌到平原 → 正常写入（对照组），落地为雷暴。

真机验证：1.18.1 自检里 **300 个用例**（15 个下界/末地/虚空群系 × 20 种天气）全部走「保持原版」分支。

原来的 `ClimateResolver` 只在「显式配置/标签/分类都没命中」时才被问到 ——

## 12. 真实时间同步（游戏内一天 = 真实 24 小时）

### 实现要点

**参考实现的相位是错的。** 本地参考（`TimeSync-fabric`）用 `mcTicks = 自午夜秒数 / 3.6` 并 mixin `getDayTime`，
但原版的 `dayTime = 0` 对应游戏内 **06:00**（日出），不是 00:00 —— 直接套用会让**真实午夜显示成清晨**。

本模组的换算（`RealTimeSyncModel`，纯计算、可离线测试）：

```
ticksSinceMidnight = 当地自午夜秒数 / 3.6          // 86400s → 24000 ticks
dayTime(一天内)     = (ticksSinceMidnight + 18000) % 24000
世界总 dayTime      = (当地日历日序号 + dayOffset) * 24000 + dayTime(一天内)
```

- **不需要 mixin**：1.18.1 与 1.18.2 都有 `ServerLevel#setDayTime(long)`（已用 javap 核对）。
  这里是**本轮之后改过的地方**：本报告早期版本写的是「每 20 刻（1 秒）校正一次即可」，
  那是改造前的结论，**现在是服务端每刻都写一次世界时间**（`WeatherController` 里明确注释「每刻都写，不做节流」），
  配置项 `timesync.intervalTicks` 已标注**【已废弃，不再生效】**。
  原因：游戏内时钟每个真实秒只走约 0.28 刻，而原版日光循环**每刻都会自行 +1 刻**，
  只要不是每刻写，服务端时钟就会在两次写入之间被带跑（旧默认 20 刻会漂 14 刻，客户端每秒被拽一次）；
  写的是一个整数、不走网络，所以每刻写没有任何代价；
- **世界天数不会被打乱**：初始化时记录 `dayOffset = 当前世界天数 - 当地日历日序号`，
  之后世界天数 = 当地日历日序号 + dayOffset。**必须按「当地」日算** —— 最初我按 UTC 日算，
  结果 UTC+8 的玩家在当地下午就会看到天数提前 +1（这条是单元测试抓到的）。

### 时区解析（三级优先）

| 优先级 | 来源 | 说明 |
| --- | --- | --- |
| 1 | 手动配置 `timezoneOffsetMinutes` | 服主说了算 |
| 2 | **天气接口返回** | Open-Meteo 的 `utc_offset_seconds` / `timezone` —— 这是**配置城市所在地**的真实时区，对专用服务器才对（服务器的系统时区往往在机房） |
| 3 | 系统时区 / 经度估算 | 单机时正好是本机时区；都没有时按「每 15° 经度 = 1 小时」估算 |

### 真机验证

```
===== 时区与时间同步 =====
开关: 开启
```

# 第四轮：离线推算质量修正 + 两版本全量回归（2026-09-13）

## 17. 本轮改了什么

第三轮之后，离线推算链路虽然「能跑」，但对照文献与实测数据后发现了 3 个真实的模型缺陷，
以及 1 个会误导排查的诊断信息缺陷。四个都改了，改完在**两个真机服务端**上全量回归。

### 17.1 ★ 昼夜温度曲线：最低温在日出，不在 03:00

**缺陷**：原实现用一条以 15:00 为峰值的完整余弦表示昼夜温度。
完整余弦强制「最低温 = 峰值 − 12 小时」，也就是**永远把最低温钉在 03:00**。
真实世界的最低温出现在**日出前后** —— 中纬度冬季日出约 08:00，夜间分支的相位差 5 小时，
折算温度误差 1~3 K。

**修复**：新增 `core/.../time/SolarDaylight.java`（纯解析式，无查表、无依赖）：

| 量 | 公式 | 精度 |
| --- | --- | --- |
| 太阳赤纬 δ | Spencer (1971) 7 项傅里叶级数 | RMS ≈ 0.01° |
| 时差 EoT | 同一组级数 | ≈ 0.5 分钟 |
| 昼长 | 时角 `H = acos(−tanφ·tanδ)`，昼长 = 2H/15 | < 1 分钟 |
| 太阳正午 | `12 + (中央经线 − 经度)/15 − EoT/60` | 含经度与时区中央经线修正 |

昼夜曲线改成**两段半余弦**（`OfflineWeatherSynthesizer.diurnalShape()`）：
日出→（太阳正午 + 2.5h）单调升温、峰值→次日日出单调降温。
降级路径：无坐标 / 无时区 / 昼长 < 4 小时（极夜）时退回固定峰值余弦。

**真机实测（杭州 30.274N, 120.155E, UTC+8, 9 月 13 日）**：

```
昼夜 +2.1°C（湿度 50% → 日较差 12.6°C，昼长 12.3 小时，
            日出 05:46、日落 18:05、峰值 14:25（降温中））
```

杭州 9 月中旬真实日出约 05:45、日落约 18:05 —— 与天文计算一致。
（峰值 14:25 = 太阳正午 11:55 + 滞后 2.5h，物理上对应地表热量收支的滞后。）

### 17.2 ★ 缓存实况必须融合「距平」而不是绝对值

**缺陷**：早期实现把缓存的实测温度直接当锚点用。

**修复**：`T = T_clim(现在) + w(h)·(T_obs − T_clim(观测时刻))`，
其中 `w(h) = 1/(1+(h/2.10)^1.20)`，h 为距今天数（实测拟合）。
反例说明为什么必须这样做：早上实测 10°C（当时气候期望 8°C，距平 +2），
到傍晚气候期望已是 18°C —— 若照搬绝对值会把傍晚温度压掉 8K。

**真机验证（把缓存观测人为老化后对比）**：

| 实况年龄 | 权重 | 可信度 | 实测输出 |
| --- | --- | --- | --- |
| 0.0 天 | **100%** | 75% | 融合 0.0 天前的实况距平 −1.3°C |
| 1.5 天 | **60%** | 40% | 融合 1.5 天前的实况距平 −1.9°C |

60% 与拟合式手算值 `1/(1+(1.5/2.10)^1.20) = 0.5995` 一致 —— 权重确实随年龄衰减，不是写死的。
超过 3 天（`BLEND_MAX_AGE_DAYS`）不再融合；超过 24 小时（`PERSISTENCE_MAX_AGE_MILLIS`）
不再把实况当作天气类型的先验。

### 17.3 日较差：ERA5 低偏差修正 + 云的削减上限

- `DTR ≈ 18.10 − 0.1398·RH%`（14 站十年 ERA5 拟合，R² = 0.797）**+ 1.5K**。
  ERA5 是 ~30km 网格平均、会平滑极值，绝对日较差系统性偏低：
  迈阿密站点平年值 7.5K，ERA5 拟合只有 5.4K。相对关系与 R² 不受影响，只做常数修正。
- `DiurnalTemperatureModel` 里修掉一个连乘 bug：原实现把「海洋性 ×0.55」与「湿度阻尼」
  **连乘**，最低压到 0.33 倍。文献实测（Dai, Trenberth & Karl 1999）云相对晴空只削减
  日较差 25%~50%，因此阻尼系数设下限 `MIN_DAMPING_FACTOR = 0.50`。
- 日较差钳制在物理区间 **4~20K**。

### 17.4 诊断信息缺陷：`test weather` 的「落地：失败或回读不一致」是错的

没指定群系时命令压根不写入世界，但原实现照样打印「失败或回读不一致」。
实机排查时这条误导性信息浪费了时间。现在三种情况分开说：

| 情况 | 输出 |
| --- | --- |
| 未指定群系 | `未写入（未指定群系 → 跳过气候校验与落地验证；先执行 /nowweather test biome <群系ID> 再灌天气）` |
| 写入成功 | `成功且回读一致` |
| 回读不一致 | `回读不一致：期望 X，实际 Y；目标群系 Z 的正常温度范围 …` |

# 第五轮：季节振幅改用「距海岸距离」模型 + 可复现性修复

## 21. 本轮改了什么

### 21.1 ★ 季节振幅：从「只按纬度」换成「纬度 + 距海岸距离」

**问题**：离线推算最大的误差来源是季节振幅。同纬度上，海洋性与大陆性气候的年较差可以差三倍 ——
实测西雅图（47.6°N，距海 75km）振幅 **7.4K**，而几乎同纬度的法戈（46.9°N，距海 1210km）
振幅 **17.1K**。只按纬度估振幅，实测 R² 仅 0.53。

**修复**：接入 `core/.../climate/CoastDistance.java`：

```
A = sin(|lat|) · (9.1 + 18.1 · sat(d))        sat(d) = d / (d + 400)
d = 到大圆上最近海洋格的距离（km，量化到 25km）
```

`d` 由一张内置的 **8,100 字节** 1° 陆海位掩码算出（Natural Earth 1:110m `ne_110m_land`，
**公有领域**，可自由再分发）。掩码本身比仓库里任何一份气候 JSON 都小，
仍然符合「离线必须轻量」的约束。

**测量结果（对 46 站实测振幅，本仓库自测实际打印的数字）**：

| 模型 | RMSE | MAE | 最大误差 |
| --- | --- | --- | --- |
| 距海岸距离模型（新） | **2.51 K** | **1.76 K** | 10.36 K |
| 只按纬度（旧，仍作降级路径） | 5.06 K | 3.79 K | 15.11 K |

**核对方式不是「看起来差不多」，而是交叉验证**：46 站标定表
（`docs/research/continentality-calibration.csv`）是**独立于本实现**产出的
（ERA5 一阶谐波拟合 + 1 km 掩膜径向搜索）。如果本实现读掩码的位序、格归属、
径向搜索步长或大圆公式写错任何一处，46 站的 `d` 和预测值会集体对不上。
`ContinentalityTests` 逐站比对的结果是：**46 站全部在容差内（距离 25km / 振幅 0.35K），0 站超差**。

**必须说清楚的取舍**：距海岸距离模型在**东亚季风型东岸会低估振幅**
（东京 +4.69K、哈利法克斯 +4.83K）—— 而这一带正是本模组主力用户所在地。
旧的「只按纬度」公式因为系数偏大，反而更接近季风气候的实际值。
这是**用全球平均精度换局部精度**的取舍，已写进测试（`knownFailureZones()`
把这三类地方写成「必须失败」的断言，而不是假装模型到处都对）。
正确的下一步是让这些群系在气候数据里显式覆盖季节振幅（`ClimateModifier` 扩展点已支持），
而不是继续调这条公式。

**真机影响**（杭州，9 月 13 日）：

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 季节项 | +6.4°C | **+4.6°C** |
| 最终推算温度 | 26.8°C | **26.7°C** |
| 与真实观测（Open-Meteo 27.2°C）之差 | 0.4K | **0.5K** |

> 注意最终温度几乎没变：因为距平融合会把「实况相对气候期望的偏离」搬过来，
> 所以振幅的修正主要影响**预报的展开幅度**（跨季节、跨昼夜），
> 而不是「此刻」的估计。这正好说明为什么「融合距平」比「融合绝对值」重要。

### 21.2 ★ 数据集生成不可复现（真 bug）

`BiomeClimate.toJson()` 写 `possibleWeather` 时直接遍历 `Set.copyOf(...)`，
而 **JDK 的不可变集合迭代顺序取决于每次 JVM 启动生成的随机 SALT**。
后果：每次重跑 `tools/gen-datasets.ps1` 都会产生 5 个 JSON 文件的字节级差异
（内容语义相同），污染整个仓库 diff，并且让人无法判断「数据到底有没有变」。

修复：序列化前按枚举名排序（生成器里汇总表的并集同理，`LinkedHashSet` → `TreeSet`）。
现在连跑两次（两个独立 JVM）**6 个产物哈希完全一致**。

### 21.3 其他清理

- **旧产品名清理（范围要说清楚）**：`core/` 与 `versions/` 的**源码已清零** ——

### 23.3 顺带发现并修掉的两个真 bug

**（1）点「保存」其实不会生效（依赖了不存在的事件）**

读 Forge 源码确认：
`ConfigValue#set()` 只调 `childConfig.set(path, value)`（写内存），
`ConfigValue#save()` → `spec.save()` → `FileConfig.save()`（写文件），
**两者都不发 `ModConfigEvent.Reloading`** —— 那个事件是 `ConfigTracker` 的文件监视器
发现「外部改动」时才发出的。旧实现的注释写着「Forge 会触发 Reloading，模组据此热重载」，
这是错的：它把「可能发生」当成了「一定发生」。

修法：`NowWeatherMod.reloadConfigNow()`（新增，界面与命令都调它），
`onConfigReloading` 反过来委托给它，两条路径共用一份逻辑。

**（2）默认值读出来是个对象**

为了做「是否已改过」与「恢复默认」，需要读默认值。
第一版用 `shadowSpec.get(path)` —— 实机打出的是
`默认 net.minecraftforge.common.ForgeConfigSpec$ValueSpec@499cfcfe`：spec 内部存的是
`ValueSpec` 对象，不是解析后的值。正确做法是用影子 spec 上的 `ConfigValue#get()`：
影子 spec 不挂文件（`childConfig == null`），此时它必定返回 `defaultSupplier`。
现在 `ForgeConfig` 在类初始化时反射枚举全部 `ConfigValue`，建出 `toml 路径 → 默认值` 的表，
所以所有默认值一个都不用抄（当轮是 52 个）—— 抄写必然漂移。

### 23.4 新增 `/nowweather config` 命令（与界面同源）

为了让「界面里的逻辑」能在专用服务端上被验证，命令与界面共用 `ConfigEntries`：
`list [分组] / get <键> / set <键> <值> / reset <键>`。
这同时也是一个真功能：不想开客户端的管理员可以直接改。

`set` 之后还会做**交叉校验**（范围校验拦不住、但组合起来不合理的配置）：

| 组合 | 提示 |
| --- | --- |
| 最短持续刻数 > 最长持续刻数 | 「天气时长会被压到最长值，建议调回来」 |
| 过期判定 < 刷新间隔 | 「数据会在两次刷新之间一直显示为过期」 |
| 接管维度列表为空 | 「等效于关闭」 |
| 关掉「下界/末地保持原版」 | 「与『这两个维度完全保持原版』的承诺相反」 |

## 27. 顺带抓到的真 bug：清空列表会写进一个 `""` 元素

用命令清空「让权模组列表」时：

```
/nowweather config set compat.yieldToModIds ""
→ toml 里得到 yieldToModIds = ["\"\""]
```

原因是 brigadier 的 `greedyString` 至少要一个字符，`""` 会**原样带两个引号**传进来，
而列表解析只是按逗号切分并把非空片段收进去 —— 于是得到「一个内容为 `""` 的字符串元素」。
这种值不会报错，只会让玩家以为配置坏了。

修复（`ConfigEntries.setFromString`）：

- 认出「清空」记号：`空` / `-` / `none` / `empty` / `clear` / `[]` / `{}` / `""` / `''`；
- 每个元素**去掉一层成对引号**（从 toml 里复制粘贴时经常带着）；
- 标量文本同样去引号。

**实测（1.18.2 真机）**：

| 输入 | 结果 |
| --- | --- |
| `set compat.yieldToModIds weather2, projectatmosphere` | `weather2,projectatmosphere` ✅ |
| `set compat.yieldToModIds none` | 空列表，toml 里是 `yieldToModIds = []` ✅ |
| `set compat.yieldToModIds -` | 同上 ✅ |
| `set sync.dimensions "minecraft:overworld"` | 去引号成 `minecraft:overworld` ✅ |
| `reset sync.dimensions` | 恢复 `minecraft:overworld` ✅ |

## 32. 查证后确认「不是 bug」的一处（记录下来免得以后再查一遍）

同一批采样里，`terralith:alpine_grove` 的**雷暴**起初被认为是 bug ——

所以雷阵雨必须允许，只有强雷暴要排除（由 `thunderBias`/`humidity` 门槛负责）。
也就是说这是**刻意设计**，我的「修复」反而破坏了它。已完整回退，并在代码里补上注释说明这段查证过程。
